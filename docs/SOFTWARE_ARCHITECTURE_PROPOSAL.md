日期：2026-10-28。状态：从零重新开发的候选架构，尚未实施。本文回答系统如何组成、各模块负责什么以及到哪里查具体合同；产品目标、完成标准和版本范围以[产品需求基线](PRODUCT_REQUIREMENTS_BASELINE.md)为准。

本轮按“架构总览 → 专题协议 → 可执行契约”组织设计。API 字段、路由和示例不在总览中重复维护。R 是已确认要求，D 是待评审设计，H 是待验证假设，P 是待定参数，F 是有版本范围的事实；生成 schema 或通过离线检查不会使 D/H/P 自动升级为已支持能力。

## 产品边界

**[R] agentd 是可信用户本机上的多模型开发协作工具。** 主线 Codex 定义目标、验收和难度；agentd 选择用户配置的 worker；原生 Claude Code 执行；外部独立 reviewer 形成判决。主线使用成果或整合代码发生在任务闭环之外。

以下边界在拆分文档后保持不变：

- PASS 即成功；第三个有效候选被 REJECT 才是审核失败，不增加采纳或整合阶段。
- 运行故障、无法审核和通知失败不冒充 REJECT；有限恢复耗尽后保留进度，允许显式继续或取消。
- 已提交合同不可改；已结束任务不可重开。调整目标、难度、验收或模型时创建关联新任务。
- 主线不指定模型；首次分配后返修和恢复沿用固定模型与执行配置。
- 复用原生 harness，不重造工具循环，不托管外部 Codex 登录、根线程或推理生命周期。
- 从零开发新代码和新状态目录；旧实现只供风险参考，不默认兼容旧 API、迁移旧任务或接管旧部署。

本机可信定位不等于任意共享写入都安全，也不构成恶意同 UID 隔离。主机宕机、磁盘耗尽和共享远端故障的保证范围必须如实说明。

## 系统组成

**[D] 使用一个业务 daemon，保持一份权威业务状态。** Dashboard 是用户配置与管理界面；CLI/MCP 是 agent 的薄客户端；它们经共同 HTTP 协议调用同一应用服务。

| 组成 | 职责及边界 |
| --- | --- |
| Dashboard | 配置、任务观察、允许动作和管理操作；不自行推断权威状态或编排升级步骤 |
| 主线 CLI/MCP | 提交、查询、继续、取消与读取成果；不拥有平台管理员或独审权限 |
| reviewer CLI/MCP | 领取冻结候选、取材、保存自有验证证据和提交判决；不写任务合同或管理 worker |
| daemon | 任务、调度、执行观察、审核、通知、配置、查询与统计的应用用例 |
| 原生 worker | 在私有工作区和受限执行组中工作，通过唯一交付通道提交候选材料 |
| 宿主监督器 | 启动门控、精确执行身份、进程观察和停止核对；不裁决任务成功 |
| 生命周期执行器 U | 在服务停止边界之外按需执行安装、升级、卸载，并保存操作接续记录 |
| SQLite 与成果存储 | SQLite 保存事务事实及索引；Git/文件保存代码、报告、证据和可恢复进度 |

一个业务 daemon 不等于只有一个 OS 进程。完整的[调用和运行拓扑图](design/RUNTIME_LIFECYCLE.md#1-系统边界入口与运行拓扑)放在运行专题。

## 模块与数据所有权

**[D] 按业务不变量拆模块，而不是按数据库表或文件数量拆分。** 不引入微服务、通用工作流引擎或消息中间件作为默认依赖。

| 模块 | 唯一拥有的事实 | 不承担的责任 |
| --- | --- | --- |
| 任务服务 | TaskSpec、业务阶段、依赖、首次 Assignment、拒绝计数与终态 | 不调用 systemd，不解释原生工具循环 |
| 调度与执行 | 模型选择、槽位与预算准入、Execution、停止/恢复观察 | 执行结束不等于任务成功 |
| 候选与审核 | 冻结候选、领取租约、判决及证据绑定 | 不增设主线采纳，也不单独提交任务终态事务 |
| 成果存储 | 内容摘要、Git 引用、保留 pin、ReadGuard 和回收 | 不更改历史判决或把文件存在当作发布成功 |
| 接入与配置 | 项目、固定配置、角色凭据、授权上下文与管理配置 | 不托管外部 Codex 账号或推理会话 |
| 通知与查询 | outbox/inbox、投递观察、UI 投影和可重建统计 | 消息送达不等于领取或完成 |
| 平台适配 | 资源组、工作区及服务/生命周期接口 | 不把平台拓扑写入任务业务合同 |

应用用例持有统一事务，所有者模块通过受限接口参与，不各自偷偷 commit。派发预留、判决计数与终态、取消意图与租约撤销等必须一起提交；慢 Git、文件复制和进程调用在事务外完成并对账。具体责任见[事务所有者](design/RELIABILITY_AND_STORAGE.md#3-跨模块调用与事务所有者)。

## 核心任务闭环

主线提交时冻结 TaskSpec；首次派发前固定 ResolvedInputs、模型和配置。两次冻结之间可以等待上游成果，但不能改取后来的任务目标、默认模板或模糊的 latest。

Task 表示业务阶段，Execution 表示一次运行，Candidate 表示一次不可变交付，Review 表示绑定该候选的独立判决。它们分开，才能让执行重启不额外消耗审核轮次。

| 事件 | 业务结果 |
| --- | --- |
| 提交 | queued；等待输入、资源和执行条件 |
| 预留并派发 | running；即使进程已中断，业务阶段也可以保持 running |
| 执行闭合且交付校验通过 | reviewing；只开放同一冻结候选 |
| PASS | finished / passed |
| 第一或第二次有效 REJECT | queued；沿用原合同、模型与已有成果返修 |
| 第三次有效 REJECT | finished / review_failed；通知主线重新规划 |
| 取消意图先提交 | 禁止派发与迟到判决；停止及租约撤销核清后 canceled |

同 Task 和同 worker 槽都至多有一个未闭合执行。审核耗尽、执行中断及未知副作用有不同恢复动作，不使用 force 绕过停止、输入或授权核验。完整[角色泳道与分支](design/TASK_AND_REVIEW_PROTOCOL.md#2-统一角色泳道与条件分支)和[恢复动作](design/RELIABILITY_AND_STORAGE.md#recovery-actions)分别维护。

## 运行边界

**[R] U 在服务 S 之外；日常启停由操作系统服务管理器负责。** **[D]** S 内分控制组 C 和逐执行 worker 资源组，不默认新增专用父资源池 P。控制余量、祖先限制及 U 同时运行的预算须在目标主机验证。

worker 使用独立工作区、配置实例、会话和临时状态。CPU、内存及 pids 覆盖受管本地后代；外部 reviewer、现有共享 MCP 服务和远端服务不被伪装成已纳入该预算。

配置拆成可变槽位准入、不可变执行配置及任务资源覆盖。资源覆盖只作用后续 Execution；取消是终态，不能当作暂停。draining 保留旧任务接续能力，disabled 使其明确等待；减少数量不得偷偷换模型或强杀任务。

共享资源一次性与槽位、预算取得；未知持有不会因 TTL 到期而释放。对未声明的任意原生写入不作自动发现保证。详细配置、停止和升级规则见[运行专题](design/RUNTIME_LIFECYCLE.md)。

## 接口与契约分工

**[R] 接口先行、前后端分模块并统一发布。** 页面仍是总览与任务、Worker 配置、服务管理三个主要页面。允许动作来自后端，点击时重新检查权限和前置条件。

契约代码独立放在 specs/agentd_v1，不导入或改写现有 agentd 应用：

| 内容 | 维护方式 |
| --- | --- |
| 请求、响应、交付清单与可表达的跨字段约束 | Python 类型定义 models.py |
| HTTP 方法/路径、角色、schema、错误、幂等、CLI/MCP 映射 | 操作注册表 operations.py |
| OpenAPI、JSON Schema、API 参考页 | 从上述源码生成，禁止手改 |
| 合法样例、反例和一致性检查 | examples 与 check.py |
| 权限、幂等竞争、文件边界及外部副作用 | 专题行为合同与后续真实实现验收 |

这是一份可执行的候选设计契约，不是新后台实现。类型校验不能证明事务原子性、真实权限、进程闭合或模型效果。V0 范围优先具体化，V1 尚未细化的生命周期 HTTP 不冒称已交付。

## 可靠性与数据原则

- 先持久记录意图，再做外部动作；DB、文件和 OS 进程不构成同一事务，结果未知时保留占位并核对。
- worker 通过唯一 delivery.json 交付；退出码和自由文本不能补造候选成功。报告任务无需 commit。
- reviewer 在独立副本验证，记录自己产生的证据；租约由候选活动驱动的显式请求延长，MCP ping 不代表审核活跃。
- 通知是提示，业务队列是权威；收件、领取和判决是不同事实。
- 历史索引不等于永久内容保留；执行/依赖/交付/显式保留等 pin 和传输 ReadGuard 保护对象，GC 与新引用竞争必须裁决。
- 恢复旧备份更换 store_epoch 和授权代次，阻止旧客户端自动重放；备份同时覆盖数据库及承诺保留的 Git/文件。
- 升级采用独立准备和受控停机切换；失败保全数据，不将恢复旧备份当作通用代码回退按钮。

故障窗口和保留算法见[可靠性专题](design/RELIABILITY_AND_STORAGE.md)，不能用几个状态字段或 HTTP 200 代替这些保证。

## 实施与验证

按“关键平台探针 → V0 契约冻结 → 一条真实任务链 → 并行与故障 → V1 能力”推进。前后端在契约确定后可以独立实现，但应尽早共同跑通配置、提交、执行、独审和结果读取。

模型完成率、成熟队列和收益口径仍由需求基线拥有。实现了并行或能力路由，不自动证明提速、省钱或优于随机；需要对应任务集和观察窗口的实验。

当前需确认的重点是首发平台、阶段限制、参数候选值和客户端/原生工具支持矩阵。它们及原始证据集中在[决定清单](design/DECISIONS_AND_EVIDENCE.md)，验收顺序、负载条件和故障场景集中在[验收计划](design/VALIDATION_PLAN.md)。离线契约检查、真实模型、真实客户端和目标主机结果分别记录，不混成一个“已通过”。

以后修改字段或路由，应改契约源码并重新生成、校验；修改状态、角色或恢复行为，应同时更新所属专题、需求影响和验收。总览只在系统边界、模块职责或关键决策改变时更新。
