# agentd 产品需求基线

日期：2026-10-27；最近补充：2026-10-28。状态：从零重新开发的需求基线，尚未实施。本文以用户本轮决定替代此前建议中关于采纳、整合、三轮返修和 benchmark 的定义；不改变正在运行的服务或历史任务。配套文件：[软件架构总览](SOFTWARE_ARCHITECTURE_PROPOSAL.md)。本文件定义产品要求；从架构总览按需进入六个专题和可执行契约，查阅实现方案、字段和验收。必要历史教训已提炼到设计专题，不要求另读旧资料。

## 决定状态与阅读规则

需求、架构专题与可执行契约共用五种标签，标签可以标在整节或单条决定上：

| 标签 | 含义 | 可以据此做什么 |
| --- | --- | --- |
| **[R 已确认]** | 用户明确确认的产品要求 | 设计不得静默削弱；变化须形成明确产品决定 |
| **[D 待评审]** | 为满足要求拟定的设计或版本取舍 | 可评审和提出替代，不视为已批准实现或已接受限制 |
| **[H 待验证]** | 依赖实际主机、客户端或模型行为的假设 | 需要探针及证据，不能用方案描述宣称成立 |
| **[P 待选择]** | 尚未确定的数值、平台组合或策略参数 | 在受影响版本开发/发布前定案，不能实现时任意选择 |
| **[F 已有事实]** | 有来源和版本范围的实现/验收事实 | 只在注明范围内成立，不自动证明新方案 |

第 2 节为 [R]；核心需求表承接这些要求。未明确确认为产品决定的算法、接口、状态编码、分期表及指标口径均为 [D]，不得因出现“必须”而升级成用户已确认要求。“必须”表示该候选设计内部的正确性条件。关键条目状态以文末决定清单及架构中的标签为准。

## 1 产品目标

agentd 是面向可信用户的本机多模型开发协作工具。用户通过主线 Codex 理解需求并拆分任务，由 Claude Code worker 使用配置的模型并行执行，外部独立 Codex 审核成果，agentd 负责可靠地推动和记录这一过程。

三个核心目标是提高任务并行吞吐、让合适的任务使用较低能力或成本的模型，以及通过任务难度与完成率让 agentd 逐步学会按难度分配模型。任务成功的唯一业务标准是独立评审通过，不要求主线采纳、代码合并或项目整体交付。

探索性工程允许主线根据实验结果重新规划和拆分任务。agentd 不预先规定所有业务步骤，也不替代原生 harness 的推理与工具循环。

## 2 已确认的产品决策

| 决策 | 明确含义 |
| --- | --- |
| 从零重新开发 [2026-10-28] | 根据本基线重新开发代码，不要求在旧实现上改造或复用；旧实现仅作历史风险与证据参考。旧 API 兼容、旧任务迁移和接管旧部署不是默认交付义务；新产品自身支持版本内的升级仍须交付 |
| 用户与 agent 的入口 | Dashboard 是用户配置和管理 agentd 的 Web UI；CLI/MCP 是 agent 使用 agentd 的入口，共用应用服务与权威状态 |
| 前后端模块与页面规模 | Dashboard 与后端分为两个开发模块，先定义交互合同、独立实现并尽早联调；同一产品统一发布。首版三个主要页面：总览与任务、Worker 配置、服务管理；详情、接入和简单统计作为子页面或面板 |
| 角色连接与无感认证 | 同一 MCP bridge 实现提供主线和独立 reviewer 两个固定角色连接，各自自动加载凭据；后端接入模块内部统一认证和授权，日常工具不要求用户或模型输入凭据。入口隔离不替代后端校验 |
| API 合同先行 | 每个对外 HTTP API 在对应功能实施前定义输入、输出、错误、权限与状态行为；复用公共约定和共享 schema，不要求每个接口独立 JSON 模板。首个可用版本合同先定案，后续版本按阶段细化 |
| 固定 worker 池 | 用户在 Dashboard 配置数量、中转站 URL、模型及参数和资源限额，保存为固定版本的 worker 配置供 agentd 选择 |
| 自动选择模型 | 主线只给任务难度，不选模型；早期各模型能力视为相同并随机分配，积累足够结果后困难任务优先分给表现更强的模型 |
| 可信用户、本机使用 | 优先处理误操作、执行故障和资源争用，不建设恶意租户之间的强安全隔离平台 |
| 保留原生 Claude Code 能力 | 在模型、账号和本机条件本来支持的范围内，worker 能使用直接运行 Claude Code 时可用的 MCP、subagent、工具、网络和会话能力 |
| worker 故障互不传播 | 代码、配置、会话和临时状态独立；CPU、内存及子进程总量受限；共享外部服务和文件的写入边界由项目约定 |
| PASS 即成功终态 | 无需主线再批准、采纳或整合；通过后主线认为不合适，创建新任务，不修改已完成任务 |
| 三次有效拒绝即失败终态 | 同一任务最多有三个被独审拒绝的候选；第三次拒绝后通知主线接管和调整任务难度，不允许第四次自动尝试 |
| 运行故障另计 | 未形成有效审核判决的接口、工具、超时、资源故障不消耗审核次数；有限自动恢复耗尽后保留任务和进度，通知主线；允许显式继续，不自动判任务失败 |
| 成果由主线使用 | agentd 保留候选 commit、分支与证据；调查任务保留报告与证据。整合在任务流程之外 |
| 简单模型 benchmark | 主线在执行前给任务难度，agentd 按模型和难度自动统计完成率，不按工具或 Claude Code 版本拆分评分 |
| 运行拓扑与升级职责 | 必须明确控制进程、worker 和升级执行者的边界；升级在 daemon 停止后仍须有明确执行和恢复责任，不因简化而遗漏旧 P/S/C 解决的问题。具体替代拓扑及停机范围按 D/H/P 评审验证 |
| 有限生命周期承诺 | 安装、退出、数据保留和明确支持版本内的升级优先；不承诺任意历史版本迁移或复杂自动修复 |

## 3 角色与责任

| 角色 | 责任 |
| --- | --- |
| 用户：业务开发角色 | 与主线 Codex 对话，确定业务目标、推进项目并接收成果；任务操作使用主线的项目权限 |
| 用户：agentd 管理与开发角色 | 通过 Dashboard 配置 worker、接入和服务；通过 Dashboard/本地 CLI 发起由 U 执行的安装、升级、卸载；在开发工作区推进 agentd 自身代码与候选版本，不直接改写正在运行的部署 |
| 主线 Codex | 拆包、定义验收与难度、经 CLI/MCP 提交任务、处理失败和重新规划；自行使用或整合成果 |
| worker | 在独立环境中执行、自检，提交候选；根据拒绝反馈修复，最多提交三个有效审核轮次 |
| 外部独立 reviewer | 领取指定候选，依据固定任务目标和验收标准提交 PASS 或 REJECT，给出证据和可行动反馈 |
| agentd | 任务持久化、根据难度及历史完成率自动选择模型和 worker、调度、执行监督、候选保存、审核排队、次数限制、故障处理、通知和统计 |
| 可选维护者 | 排查平台故障，不参与普通任务的日常审批 |

上述两个用户角色由同一个人承担，不要求两个用户账号；业务主线连接与平台管理授权仍分离。agentd 自身开发不等于业务主线获准管理宿主服务，构建候选也不等于完成安装或升级。

主线通过已有 Codex 客户端建立独立 reviewer 根线程，并接入 agentd CLI/MCP。agentd 不管理外部 Codex 登录、创建自己的 Codex harness 或把主线与 reviewer 合成一个会话。

## 4 任务合同与结束语义

**[D 待评审] 提交和派发采用两阶段冻结。** 提交时固定 TaskSpec：项目、目标、范围、成果形式、验收标准、主线评定难度、显式输入引用、依赖选择规则、工具/MCP 需求及运行恢复策略；此时尚不要求上游成果已存在。首次派发前固定 ResolvedInputs：实际 base commit、上游已通过候选、成果内容标识和保留引用。主线不提交模型选择；agentd 在首次派发时绑定实际 worker、模型、固定配置版本及资源限额，作为执行记录的一部分。代码任务应指定 base commit；调查任务应指定可访问材料及报告期待。

任务提交成功即固定目标、难度、验收标准和依赖选择规则；首次派发时再固定解析输入及 agentd 分配的模型。同一任务内返修只改变候选，不改变任务合同。需要重新分配模型、调整难度、修改验收或重新拆包时创建新任务，由 agentd 为新任务选择 worker，并保留与原任务的关联。草稿仅存在于 Dashboard 表单、CLI 文件或主线上下文，不是服务端 Task，没有 draft 状态或编辑接口。queued 任务也不可改合同；提交错误时取消原任务并新建关联任务。终态任务不可重开或覆写。CPU/内存等运行条件可经明确操作调整并记录，不改变业务合同，也不要求另建任务。

| 结果 | 条件 | 后续动作 |
| --- | --- | --- |
| 成功 | 对当前有效候选的独立审核 PASS | 保存终态与成果，通知主线；是否使用成果由主线决定 |
| 审核失败 | 第三个有效候选被 REJECT | 保存失败终态，通知主线；主线调整任务难度或拆包后新建任务 |
| 已取消 | 主线或用户取消，相关执行完成停止核验 | 保留已有证据，从正常完成率分母中排除并单独展示 |

运行意外中断不是终态。保存工作区、未提交修改、原生会话引用、日志和审核次数；自动恢复额度耗尽只停止自动尝试，通知主线修复条件后显式继续。先确认旧执行及后代停止、核对不明副作用，再恢复原会话；原会话不可用时可新建会话接手已有成果。资源不足可调整资源后继续同一任务。

审核无法进行、reviewer 暂时离线、传输失败均不等于 REJECT。审核恢复使用独立、有界的操作策略；耗尽后保留审核阶段并展示等待原因，由主线选择恢复或取消，不能静默循环或将其计作模型语义失败。任务状态只保留 queued、running、reviewing、finished、canceled；运行中断、等待和停止过程作为执行观察或操作记录，见[状态与角色泳道](SOFTWARE_ARCHITECTURE_PROPOSAL.md#核心任务闭环)。

三次机会的示例：候选 1 被拒 → worker 修复 → 候选 2 被拒 → worker 修复 → 候选 3 被拒 → 任务失败。任何一次 PASS 立即成功。相同请求重发、同一候选重复判决和审核领取超时均不增加轮次。执行重启、会话重建不能重置任务的已用轮次。

终态不可变指目标、候选、判决、结果和计分事实不可覆写。允许追加后续任务链接、评论、归档或发现问题的记录，但不能因此撤销原终态。若审核通过后发现缺陷，另建关联任务，保留原判决的历史事实。

## 5 核心功能需求

接口遵循深模块原则：Dashboard 面向用户配置与管理，CLI/MCP 面向 agent 的业务动作；内部完成幂等、择模、候选绑定、审核租约及通知恢复，不要求主线逐步编排。接口、通知、可靠性及历史教训统一见[软件架构总览](SOFTWARE_ARCHITECTURE_PROPOSAL.md)。

| 编号 | 需求 | 验收要求 |
| --- | --- | --- |
| F01 | 创建和查询任务 | CLI/MCP 共用权威数据；重复创建请求不重复生成任务；主线退出后任务仍存在 |
| F02 | 自动分配与并行调度 | agentd 从用户配置的 worker 池选择执行者；冷启动随机分配，样本足够后困难任务优先选择表现更强的模型；每个 worker 同时最多执行一个任务，每任务最多一个活动执行；容量不足排队，审核积压可限制新增派发 |
| F03 | 原生 worker | 验证文件读写、shell、MCP、subagent、网络及项目所需其他原生功能；不另造通用工具循环，不把所有工具改写为 agentd 专用 recipe |
| F04 | 独立执行环境 | 每任务独立工作区、配置实例、会话与临时目录；配置可从主线模板继承，任务写入不修改模板或其他 worker |
| F05 | 资源保护 | worker 及本地后代进程共享该 worker 的总预算；单个 worker 崩溃、超限或取消时，其他任务可继续；为 daemon 和主机保留余量 |
| F06 | 成果保存 | 代码候选对应可获取的 commit/分支及证据；报告对应不可变产物；工作区回收不删除仍需交付的成果 |
| F07 | 独立审核 | reviewer 经 CLI/MCP 领取冻结候选和完整相关证据，提交绑定该候选的判决；worker 不能自审，过期结果不生效 |
| F08 | 三轮闭环 | 拒绝自动反馈 worker；第三次拒绝原子地结束任务并产生主线通知；不存在额外的“三次返修额度” |
| F09 | 通知与唤醒 | 对既有 reviewer 根通知待审工作，对主线通知成功、失败与受阻；队列持久化，通知成功不等于领取；通知失败仍可主动查询 |
| F10 | worker 池配置 | 用户在 Dashboard 设置 worker 数量，以及各 worker 的中转站 URL、凭据来源、模型和模型参数、资源限额；生成固定配置供 agentd 选择，更新生成新版本且不覆盖已绑定任务，密钥不写入公开任务材料 |
| F11 | 有界故障恢复 | 接口故障、崩溃、超时、工具和资源错误分类；自动恢复有总次数与时间边界；耗尽后通知主线而不结束任务；支持保留进度的显式继续，副作用不明时等待核对，不盲目重跑 |
| F12 | Dashboard Web UI | 前后端分模块、接口先行、统一发布；三个主要页面及子面板覆盖功能，后端提供权威状态与动作可用性；作为用户配置与管理 agentd 的入口，管理 worker 池及服务设置；展示任务阶段、实际 worker 执行情况、当前轮次、等待原因、结果、资源和模型完成率；与 CLI/MCP 状态一致，不显示采纳/整合为必经阶段 |
| F13 | 基本工具复用 | worker 可使用主线配置的工具/MCP，并在自己工作区开发工具；共享版本由主线选择，worker 不直接覆盖其他 worker 正在使用的工具 |
| F14 | 任务依赖 | 可声明上游；上游 PASS 才满足成功依赖，失败使下游受阻。代码输入必须明确指向可用成果，不能把 PASS 当作已经合并代码 |
| F15 | 运行拓扑与资源归属 | 区分服务控制面、worker 及其后代、外部 Codex、升级执行者；worker 超限不应挤垮控制面，停止服务不应终止正在负责升级的执行者；不能把未纳入的外部进程计为受管预算 |
| F16 | 生命周期执行与中断接续 | U 统一管理安装、升级和卸载，日常启停由服务管理器负责；新版本独立准备，不覆盖正在运行的代码/依赖；切换前停止新增派发，核对在途执行和数据库写入，备份后切换；各生命周期操作的步骤和结果持久记录，终端/daemon 退出不丢失执行所有权 |
| F17 | 升级兼容和失败保全 | 不兼容版本在切换前拒绝；失败保留原版本、数据和维护状态；是否回退由数据库兼容及切换后写入决定，不自动恢复旧备份覆盖新成果 |

**[D 待评审]** 依赖绑定具体上游 Task ID 和明确产物选择规则；拒绝不存在、自依赖、成环及未授权跨项目依赖。上游失败/取消使下游保留 queued 并说明原因，不传染成任务失败；成果不可获取或损坏时不得派发。关联新任务不会替换旧依赖；如需替换，取消未结束的下游并新建 TaskSpec，不热改依赖。详见[双阶段输入冻结与依赖](design/TASK_AND_REVIEW_PROTOCOL.md#5-双阶段输入冻结与依赖)。

下游可以引用上游通过的精确成果。需要合并多个代码候选时，由主线在流程外准备确定的 base，或创建明确的整合任务；agentd 不自动推断可以合并，也不在原任务后追加隐藏整合阶段。

### 5.1 交付链补充验收

**[D 待评审，2026-10-28]** 下表补齐既有 F01–F17 的可执行含义，不增加另一套业务闭环。具体字段、协议与探针由架构正文拥有。

| 对应需求 | 补充行为 | 首次交付时的验收 |
| --- | --- | --- |
| F01/F10/F12 | 项目、仓库、凭据来源、worker 和角色可以通过明确的本地安装/管理接口完成首次接入；公开写操作均能按原 request_key 核对结果 | 从新状态目录完成配置到真实任务，不依赖旧库、隐藏手填表或聊天中粘贴密钥；响应丢失不会重复创建任务或领取 |
| F03/F06 | worker 使用显式、有版本的输入与交付合同；代码与报告交付分别校验，退出 0 不等于候选有效 | 代码提交、无 commit 报告、缺交付文件、非法成员和交付写到一半均有确定行为；无效交付保留进度，不计 REJECT |
| F06/F07 | 独审能取得冻结候选的独立检查副本，并保存 reviewer 自己的验证记录；候选原件不可被测试改写 | reviewer 对精确候选运行验收并提交自己的证据；不能把 worker 自检记录称为独立复验；缺测试条件使用 defer |
| F07/F09/F11 | 审核持有有 TTL 和总时长边界；传输存活不等于审核活跃；审核恢复额度耗尽仍有显式恢复入口 | 长审核、一次性 CLI 退出、bridge 活着但不工作、断线重领都不重复计分；主线可重新启用原候选审核而不重跑 worker |
| F10/F11 | 固定执行配置与任务资源调整分离；恢复操作明确处理副作用核对、会话接手及同合同重新执行 | 原任务内存不足后可提高下一次执行预算，模型与输入不变；删除/停用槽位不静默迁移模型；未知副作用不能仅点击继续就绕过 |
| F04/F05 | 共享资源声明参与派发准入；只能对遵守同一声明/命名空间约定的参与者作协调保证 | 冲突任务不同时取得同一独占资源；崩溃或 TTL 到期不直接释放未知持有；外部 reviewer/远端服务的边界明确 |
| F06/F17 | 历史索引与内容保留义务分离；期限内、执行中或依赖中的成果受保护 | 工作区清理不丢交付成果；可过期内容按明确策略处理并留下历史记录，不能把“已过期”误报“损坏”；备份恢复同时验证内容和索引 |

这些验收覆盖实际支持的 V0 功能；依赖、自动通知、自动恢复和完整升级仍按第 9.1 节在 V1 交付。独立验证使用外部 reviewer 的已有工具，不要求 agentd 托管 reviewer，也不把外部检查进程计入 worker 限额。

## 6 隔离和资源边界

可靠性目标是防止单个 worker 的普通故障扩散，不承诺宿主宕机、全局磁盘耗尽或共享远端服务故障下其他任务仍能成功。

- 独立 worktree 复用 Git 对象，输入切片和只读依赖按需共享；共享 Git 元数据的管理操作由服务协调，worker 不直接清理其他工作区。
- worker 的本地 MCP server、subagent、shell 和构建子进程尽量纳入同一资源边界；外部共享服务不冒充已纳入该限额。
- 需要写共享文件、端口、数据库或远端服务时，使用任务独立命名空间、专用实例或串行租约。无法声明安全共享方式时，应拒绝派发已知冲突的并行任务并说明原因。**[D 边界细化]** 不拦截所有原生工具调用，也不声称自动发现任意程序未声明的共享写入；支持并行的项目须提供可验证的资源声明和配置。外部参与者不遵守同一约定时，内部租约不构成全域互斥保证。
- 配置独立不要求每个任务重新登录。允许使用用户已有、明确授权的凭据来源，但不能把共享凭据的可写状态当作任务私有状态。
- 磁盘采用容量预留、日志上限、保留策略和低水位停止派发；硬磁盘配额不是新基线默认前置条件。这不等于软管理能完全阻止任意程序耗尽宿主磁盘。
- 原生能力的可用性不代表任意破坏性操作获准执行。原生授权方式与项目共享资源约定共同确定可执行范围。

## 7 benchmark

本节的分组方向为 [R 已确认]；指标、抽样和准入公式为 [D 待评审]，观察窗口等数值为 [P 待选择]。完成率可描述已审核结果，但不能单独作为提效、省钱或能力优先派发的证明。

### 7.1 维度与数据

仅以模型和主线事先评定的任务难度作为核心分组。工具、MCP、Claude Code 版本不作为评分维度或资格门槛；普通诊断信息也不因此增加 benchmark 复杂度。统计反映本地实际任务上的模型完成表现，不作纯模型因果能力证明。

**[P 待选择]** 建议采用下列 1–5 级难度量表作为初始约定，量表可在后续需求审阅中调整：

| 等级 | 主线评定参考 |
| --- | --- |
| 1 | 局部、明确、低不确定性的修改或查询 |
| 2 | 单模块常规功能或缺陷修复，需要有限上下文 |
| 3 | 多文件或跨模块修改，需要理解接口与回归影响 |
| 4 | 较高不确定性、跨模块推理或明显设计取舍 |
| 5 | 探索性问题、复杂系统交互或难以预判路径的工程任务 |

主线提交难度和简短理由，不由 agentd 自动推断。结果产生后不追改难度；主线重新判断过难时创建新任务并给新难度。模型身份使用所配置的明确标识，别名切换到不同模型时另登记模型标识，避免把不同模型混成一组。

### 7.2 完成率

对每个模型和难度组，记评审通过的任务数为 S，三轮审核失败的任务数为 R。

- **任务完成率**：`S / (S + R)`。仅统计获得最终审核结果的任务，分母为零时显示“暂无数据”。
- 同时展示 S、R、取消数和未结束任务数；未结束任务再展示执行、审核、等待及中断情况，避免高完成率掩盖长期中断任务。
- 中断不计成功或失败；同一任务恢复后最终通过只计一次成功。三轮候选不是三个 benchmark 样本。
- 运行故障次数、原因、受影响任务数和中断等待时长单独展示；因故障最终被取消的任务仍保留原因，不能隐藏其运行表现。
- 后续任务是独立任务，但保留原任务关联；汇总显示关联重拆任务数量，避免把反复拆包误读为完全独立样本。
- 不自动改任务难度或历史判决；允许依据完成率调整后续任务路由；agentd 据此更新后续新任务的分配偏好，主线仍负责业务拆包。

该完成率反映已结束审核的任务表现，不代表所有已提交任务都已完成。首版不加入 IRT、工具校正、harness 校正、自动晋级或费用归因模型。

### 7.3 从随机分配到按难度分配

1. 用户配置可用 worker 池；agentd 先过滤禁用、忙碌、连接不可用或不满足任务运行条件的 worker。资源等待与模型能力评分分开处理。
2. 冷启动时不预设模型强弱。建议先在当前有合格空闲 worker 的不同模型间等概率随机，再在该模型的合格 worker 中随机选择，避免同一模型配置更多 worker 就被当成能力更强。
3. 数据按模型和难度积累。不能仅按经过多少天切换策略；满足第 7.5 节的成熟样本和可比性门槛、差异足以支持判断时，才对相应难度启用能力偏好；不得仅按 S/(S+R) 排名。样本少或差异不明确的组继续随机。
4. 困难任务优先派给在相应难度上表现更强的模型，不根据简单任务的高完成率直接认定它擅长困难任务。简单任务仍可分给其他模型，避免全部工作集中到一个模型。
5. 建议保留少量随机探索，为新模型和样本不足的模型积累结果，避免早期偶然成败永久锁定路由。最低样本量、差异判定和探索比例留待确定，不在本文虚设阈值。
6. 任务首次绑定后，返修和中断恢复继续使用该模型及配置；新的能力统计只影响未绑定的新任务。每次分配记录随机或能力优先的理由、采用的统计和策略版本，便于解释。

等待强模型还是使用其他空闲模型的规则尚需确定。基础建议是在合格空闲池内优先；无任何合格空闲 worker 时排队，不突破用户配置的数量或限额。此处为调度策略建议，不改变用户已确认的自动分配方向。

### 7.4 少量效果指标与首版证明边界

**[D 待评审]** 不建设复杂评测平台，但从首个内部版本起保存提交、首次分配、执行、待审、中断、终态时间和可得 usage；后补记录无法补回已丢失的真实成本与等待。

| 产品目标 | 最小指标与口径 | 能证明什么 / 不能证明什么 |
| --- | --- | --- |
| 并行吞吐 | 同一预定任务集的总墙钟时间，及固定观察时间内 PASS 数；与串行基线比较 | 对相同输入、验收和资源预算记录比较；若并行增加资源需注明。仅进程重叠不能证明提速；部分未结束时不能宣称整个任务集加速 |
| 交付时延 | 提交到审核终态的耗时，成功和三轮失败分列；中位数/分位数同时给样本量 | 包含排队、审核、中断等待，不暂停总时钟。取消单列取消耗时；未结束给年龄分布，不能从延迟样本中悄悄消失。小样本不强报分位数 |
| 实际 token 消耗 | 按任务与角色记录 input/output/cache/reasoning 等原生可得字段、来源和完整性；汇总全部尝试及返修 | 去重累计 usage 与增量、避免 subagent 汇总与子会话双计。缺失为未知，给覆盖率；只拿到 worker 数据时只能报告 worker tokens，不能叫全链路总量 |
| 成本目标 | 首版报告每个 PASS 对应的该批任务已知 token 消耗，失败/取消/中断消耗不丢弃 | 不同模型 token 单价和计量可能不同；token 减少不等于费用降低。没有可靠价格及完整用量时不声称省钱，也不要求把 token 作为路由权重 |
| 调度学习收益 | 同难度、同观察窗口的能力策略与随机基线对比：按期 PASS 比例、终态时延、已知 tokens 和覆盖率 | 固定策略版本并保留随机对照，记录初次策略分配，不能把后验挑出的成功样本作比较。无有效对照时只说明策略改变了分配，不宣称优于随机 |

内部版本可证明任务链是否正确、真实并行是否发生、可得的时延及用量；正式版本可证明所支持场景内的能力策略机制工作。**实际提速、省钱、优于随机均需对应实验；功能发布与产品收益证明是两类结论。** 不预设未经测量的改善百分比。

### 7.5 防止未结束任务抬高模型分数

**[D 待评审]** 保留 S/(S+R) 作为审核结果统计；路由不直接使用它作为唯一分数。采用简单固定窗口队列统计，不推断未结束任务的语义成败：

1. 为每次初次 Assignment 记录模型、难度、时间、策略版本及随机/能力策略组。比较模型时使用已走满观察窗口 H 的同难度首次分配队列；H 在采样前确定，同组相同。没有走满 H 的任务不进成熟队列，而不是有结果的任务提前入组、没结果的继续等。
2. 对成熟队列，令 N 为全部首次分配任务数、S_H 为分配后 H 内 PASS 数。报告 `S_H/N`，同时报告窗口内三轮失败、取消和仍未完成的比例。中断或取消留在分母，H 后通过不会回写“按期通过”历史；这不改变 Task 的最终通过或失败语义。
3. 产品端另以提交时间建立相同窗口队列，把未分配任务也纳入，以免隐藏调度排队。分配后的模型指标与提交后的产品指标不得混用。
4. 启用某难度的能力偏好前，检查各候选模型的成熟样本量、可比难度、窗口及采样方式；取消/外部故障比例异常或样本不可比时保持随机并显示原因。不能通过筛掉故障任务让剩余模型显得更好。故障分类单列，不把按期未通过自动称为模型语义失败。
5. 建议在可比较任务中保留有限随机对照，并在首次调度策略分配时标记；等待、取消或未完成仍计入原策略组。共享 worker 池引起的相互影响要注明；单次前后对比不提供因果改善证明。
6. 模型偏好以成熟队列的按期通过表现为主要依据，审核结果完成率和时延辅助解释；必须达到预定样本及差异门槛，不能因原始比例略高就切换。首版仍不按工具或 harness 版本分组，不引入 IRT。

**[P 待选择]** H、最小成熟样本、差异门槛、取消/故障异常判据和随机对照比例须在能力路由实施前确定；未定或未满足时只用随机策略。这只是降低选择偏差的可审查方案，不能完全消除同难度任务内容差异。

## 8 工具成长与有限生命周期

### 8.1 工具与基础运维

工具汇总与优化保留为进阶需求：worker 提交工具候选，独立审核后由主线决定共享版本，后续任务显式选择。基础阶段做到工具可用、版本不串用和成果可交付即可；不要求建设自动推荐、消费者资格或包管理平台。

服务生命周期的有限范围建议为：单用户本机部署、启动/停止、状态查询、一致备份、保留数据卸载，以及明确支持版本间的升级。升级前检查兼容性，不支持则拒绝并给出说明；不自动接管任意旧库，不丢弃数据以求启动成功。卸载默认保留任务、成果和配置；整库、任务历史的自动清空与任意历史转换暂不纳入；按明确配置的保留期限回收成果内容见[历史索引、保留义务与回收](design/RELIABILITY_AND_STORAGE.md#10-历史索引保留义务与回收)，不等于清空历史。

具体首发操作系统、故障重试次数、任务成果保留天数和升级版本窗口留作实现前参数决策，不扩展本轮产品范围。

### 8.2 生命周期执行与运行拓扑要求

**[R 已确认，2026-10-28 补充]** 安装、升级和卸载统一由独立生命周期执行器 U 管理；U 按需运行，位于服务 S 的停止边界之外。日常启动、停止和重启由操作系统服务管理器管理 S，不要求启动 U；U 在生命周期操作中复用同一启停机制。S 是被管理的服务，不是启停操作的执行者。

**[R 已确认]** 运行拓扑和升级能力是本次需求的一部分，不能只写“支持升级”而没有 daemon 停止后的执行者与恢复责任。**[D 待评审]** 本基线建议支持“运行时准备新版本、受控短暂停机切换”，不默认承诺 worker 不停的热升级。

| 能力 | 建议支持范围 | 用户可观察结果 |
| --- | --- | --- |
| 在线准备 | 旧服务可运行时，在独立版本目录构建/校验新版本；准备任务也有限额，不能挤垮业务 | 准备失败不停止旧服务；用户看到候选就绪与缺项，而非误报升级成功 |
| 切换版本 | 停止新增派发，等待已有 worker 安全闭合，或由用户明确取消；短暂停止 API/服务，备份、切换、验证后恢复 | 任务、轮次、成果、角色和既有用户暂停保留；待审任务无需先全部 PASS，但旧租约必须按协议处理 |
| 生命周期执行独立 | U 统一执行安装、升级、卸载，在 S 的停止边界之外固定自身运行版本；首次安装不依赖 daemon，卸载不提前删除 U 自身环境 | 关闭 Dashboard、CLI 终端或停止旧 daemon 后，已受理操作仍可通过固定 operation_id 查询/接续 |
| 失败恢复 | 持久记录最后确认步骤、版本、备份和锁归属；不能证明安全时保持维护等待 | 不猜测成功，不盲目启动第二个 daemon；回退条件不满足时说明原因并保留数据 |
| 不纳入本轮默认承诺 | worker 持续执行时热换 daemon、双版本并行写同一库、任意旧库转换、永不停机 API | 必须另立设计和验收，不能从“支持运行中升级”或“有 P/S/C”推导已经支持 |

拓扑必须明确控制面与执行面资源归属，并为升级准备/执行预留可用资源。外部主线和 reviewer 的 Codex 进程不由 agentd 接管；它们的开销不伪装成 agentd 已控制的预算。保留还是移除独立父资源池 P 属于实现选择，不得省略原来由它承担的资源约束说明。

安装、升级和卸载共用生命周期操作锁，各自状态存放在任务数据库之外的持久操作记录中，服务停止时仍可查询；该记录不变成第二个任务事实源。首次安装由本地命令发起；升级和卸载可由 Dashboard 或本地管理命令发起，入口仅转交 U。停机期间 Dashboard 可暂时不可用，受信本地管理命令提供同一操作的查询和接续；不要求用户启动维护 Codex 或人工编辑数据库。

具体资源拓扑、独立执行器形式和数据库锁交接为 [D]，目标主机上关闭原服务后升级执行者能否继续、控制面是否能承受 worker 超限、断电后能否核对操作为 [H]，预算、排空时限及支持升级窗口为 [P]。拓扑、锁交接及安装升级合同集中在[运行边界与生命周期](design/RUNTIME_LIFECYCLE.md)。

## 9 版本范围与验收

### 9.1 版本范围表

**[D 待评审，须用户接受阶段限制后定案]** V0/V1 表示交付边界而非时间承诺。完整产品要求不因分期删除；开发者不能自行把未完成能力改标“后续”。架构验收章节引用本表，不再另设范围清单。

| 能力 | V0 首个内部可用版本 | V1 首个正式支持版本 | 后续明确不阻塞 V1 的能力 |
| --- | --- | --- | --- |
| 使用场景 | 单用户、单主机、单项目；相互独立任务，输入在提交时可取得 | 同一已验证主机环境；支持固定 ID 的依赖 DAG 与双阶段输入冻结 | 跨主机、多租户和任意可变依赖不在承诺内 |
| 用户/agent 入口 | 三个主要页面：总览与任务、Worker 配置、服务管理；详情/接入/简单统计作为面板，含配置、角色、任务继续/取消及暂停/恢复派发；服务管理仅状态和本地维护说明，不含升级/卸载按钮；MCP 完整跑主线/审核，CLI 是同服务的薄操作入口；不建设 CLI 交互向导 | 沿用三个主要页面，补齐故障/能力分配说明及升级/保留数据卸载操作；公开 CLI/MCP 核心操作逐项一致验收 | 丰富报表、批量向导和界面定制 |
| 并行和原生能力 | 三个真实 worker 重叠执行，至少两种可用模型；read/edit/shell/MCP/subagent 保留并验证；独立工作区与资源遏制 | 支持矩阵内的同等能力及原生兼容、真实故障隔离验收 | 更多平台或特殊外部工具组合 |
| 模型分配 | agentd 随机；采集难度、完整任务状态及可得 tokens；能力学习暂不启用 | 实现成熟队列门槛和能力偏好、随机对照及分配解释；样本不够自动保持随机 | 复杂能力估计、工具/版本校正和费用优化不在本基线内 |
| 审核与终态 | 外部 reviewer 主动领取；PASS、三轮拒绝、幂等和取消完整 | 相同语义；真实客户端在线空闲根可接收提示并领取 | 不承诺自动启动已关闭客户端 |
| 通知 | 持久 inbox/outbox、通知异常可见；允许人工打开客户端并主动查队列 | 至少一种已验证客户端传输，离线和不确定发送有确定行为 | 更多客户端适配、客户端陈旧队列清除 |
| 中断与恢复 | 保留进度、确认停止、显式继续和取消必须可用；daemon 重启可核对，未知则等待；允许自动恢复次数设为 0 | 已分类可安全恢复故障的有限自动恢复，额度耗尽后显式继续；进程窗口表逐项验收 | 通用故障自愈和复杂历史修复不做 |
| 输入、成果与工具 | 显式不可变输入；冻结候选、证据读取和保留；默认 retain，明确配置期限后按 pin 保护回收内容；可用原生工具并产出工具代码 | 静态依赖解析、保留引用及损坏诊断，主线可选择已审工具成果复用 | 自动工具推广/推荐平台 |
| 安装与数据 | 一个经验证的源码构建及本地命令调用 U 安装路径；U 首先交付最小安装能力，尚不交付升级和卸载流程；运行拓扑、资源归属和停止边界明确并实测；本地停止、备份与恢复核验；新状态目录 | U 统一执行可重复安装、升级及保留数据卸载；在线准备/排空/停机切换、操作记录和故障接续、明确支持窗口；不支持版本在写库前拒绝 | 任意旧库转换、整库/任务历史自动清空、worker 不停的热升级 |
| 效果证明 | 同一任务链、并行/串行对照记录、时延和 token 覆盖率可导出；允许结果不显示收益 | 真实任务数据记录；能力策略机制可验证，收益不足或样本不足必须如实报告 | 经济收益结论依赖实际账单与对照数据，不以复杂评测平台补空缺 |

### 9.2 阶段限制和退出条件

- **不能降低的边界 [R]**：PASS/三轮规则、主线不选模型、原生能力、单 worker 故障不破坏其他任务、已结束任务不可改、中断可继续。实现这些边界所需的身份范围、幂等、停止核对和成果完整性检查不能因 V0 省略。
- **需要用户接受的 V0 限制 [D]**：单项目/独立任务、仅随机择模、主动领取而非已验收自动唤醒、自动恢复可以为 0、仅源码构建后本地命令经 U 安装，尚无升级/卸载流程承诺。这不是开发者实施时的默认免责清单，未接受前不能将 V0 称为已满足完整需求。
- **V0 退出条件 [D]**：表内 V0 功能全部交付；真实任务经 Dashboard 配置、主线提交、并行执行、外部独审到终态；三轮、取消、重启后显式接续和关键崩溃窗口有证据；权限隔离与成果校验通过；限制在界面和说明可见。mock 不替代真实旅程。
- **V1 退出条件 [D]**：表内 V1 功能及其支持环境全部验收，关键外部假设 [H] 有实际结果，参数 [P] 已定案；没有以人工改库或维护模型常驻才能完成的正常路径。样本不足时可以发布具备冷启动回退的学习机制，但必须写“实际策略收益未证明”，不能声称已优于随机。
- 任何未通过项只能保留阻塞或另作显式范围决定，不能由开发者在报告里改写退出条件。

**前后端交付规则 [R]**：先定义页面动作及请求/返回、异步进度、权限、幂等、版本冲突和断线恢复合同，再分别实现；尽早以真实后台跑通“页面配置 worker → 主线提交 → 执行与独审 → 页面读取结果”。前端 mock、后端单测或单独页面展示不能替代该链路。页面归并不豁免已有功能；此次确认页面与模块边界，不代表其他尚待评审的 V0 限制已获接受。

**接口设计退出条件 [R]**：本阶段所有对外 API 均有明确方法/路径、角色范围、参数及请求/响应 schema、HTTP 状态与错误、前置条件/副作用、重复与竞争行为和关键示例；公共约定可引用复用。任务模板与接口样例一致，GET 不强制请求体。接口目录和前端 mock 不等于合同完成；精确 schema 从唯一类型化定义导出，不能各入口分别手写。维护规则见[所有对外 HTTP API 的合同设计规则](design/INTERFACE_GUIDE.md#13-所有对外-http-api-的合同设计规则)；精确字段和路由见[可执行契约](../specs/agentd_v1/README.md)。

### 9.3 全产品验收场景

1. 三个真实 worker 并行执行；其中一个崩溃或资源超限，其他两个仍可提交并通过审核。
2. worker 实际调用项目所需 MCP 与 subagent；本地后代资源归属可核对，不能只用 mock 宣称原生兼容。
3. 第一轮或第三轮 PASS 均立即成功，没有待采纳阶段；主线不使用成果也不影响结果与完成率。
4. 三次 REJECT 后任务失败并通知主线；不能自动开始第四轮。重复请求、重启和会话重建不重置计数。
5. 任务因进程退出、断网、资源超限或主机重启而意外中断后保留工作区和会话；自动恢复耗尽不结束任务，主线可调整资源并显式继续。原会话不可用时新会话接手已有成果，审核次数不重置；取消、未知进程和审核离线不伪造 REJECT。
6. 已成功或失败任务不能改合同、模型、难度或终态；后续调整创建关联新任务。
7. 关闭主线或 reviewer 客户端不丢任务；恢复后可查询队列与成果，重复领取/通知不会导致重复判决计分。
8. 模型与难度分组的统计能从任务终态重新计算，缺样本、中断未结束和取消均准确显示；恢复后只计一次最终结果。
9. Dashboard 保存指定数量的固定 worker 配置；主线仅给任务和难度，agentd 完成选择。冷启动不预设强弱，积累足够分难度结果后改变新任务分配偏好，既有任务模型不变。
10. 工作区回收后仍能获取保留的候选与报告；卸载保留数据，不修改外部主线仓库或 Codex 根线程。
11. 在所选运行拓扑上，单 worker 资源超限不使控制面失去响应；在线准备失败不停止旧服务；受理升级后关闭发起终端或停止旧 daemon，独立执行者仍能完成或通过原 operation_id 接续。
12. 无 daemon 时可通过本地命令启动 U 安装；卸载停止 S 后 U 仍能完成并保留约定数据及操作记录；日常启停不启动 U，生命周期操作期间冲突命令不能旁路锁与维护屏障。
13. 在排空、备份、切换、新版启动等边界注入中断，确认不重复启动 daemon、不把旧备份覆盖到已有新写入的数据上、不解除用户原有暂停；待审候选和任务次数保留。

### 9.4 历史故障形成的交付质量门槛

**[D 待评审]** 以下细化已有需求，不新增平台功能，也不改变 V0/V1 分期。P0 在相关能力首次交付时验收；P1 随相关配置、诊断和运维能力验收。历史事实、适用版本及验证方法集中在[历史复查补充：按重要性约束实现](design/DECISIONS_AND_EVIDENCE.md#13-历史复查补充按重要性约束实现)，无需另查历史文件。

| 优先级 | 必须防止的问题 | 对应需求与可观察结果 |
| --- | --- | --- |
| P0 | 审核输入或成果被静默截断 | F06/F07：目标、验收、候选和必要证据完整可取，原始字节无损；摘要不伪装完整材料；格式或读取故障不计 REJECT，不阻塞其他候选 |
| P0 | 控制面因重工作或积压失去响应 | F05/F11/F15：有界解析、后台作业和排队；重负载下仍可查询和受理取消，不能只证明 worker 有资源限额 |
| P0（V1） | 坏版本无法通过自身入口修复 | F16/F17：业务 API 不可用仍可从本地维护入口读取原升级记录、诊断及准备修复；接续保留原锁、闭合、兼容和暂停约束，不要求先伪造健康 |
| P0 | 安装与原生能力各自通过，但实际任务跑不通 | F03/F04/F16：使用独立发布目录、生成配置、真实 CLI、任务工作区和授权工具验收；禁用组件不阻断基本启动，健康与业务可用分别显示 |
| P0 | 服务准备代码时隐式执行仓库程序或传出管理凭据 | F04/F06：服务的 Git 管理与 worker 的原生执行分别限定环境；控制隐式程序调用，成果采集不改变原始内容 |
| P0 | 准备后条件变化仍然派发 | F02/F11：耗时准备后重核暂停、取消、授权、输入与容量；条件变化不启动，未知执行不重复派发 |
| P1 | 配置与真实行为不一致，正常配置变更阻断启动 | F10/F12：区分请求值、生效观察与未知；任务固定配置、调度启用状态及部署身份分别绑定；不可用 worker 不妨碍用户进入 Dashboard 修复 |
| P1 | 信号误判或原始错误丢失 | F03/F11/F12：无输出不直接判失败，SIGKILL 不直接等于 OOM；保留脱敏首错、观察值及清理结果；执行正常仍须独立审核 |
| P1 | 近似探针或开发环境冒充支持环境 | F03/F15/F16：实际发布入口与主机路径验证；记录目标故障是否真正注入、版本和 NOT RUN，不挪用其他产物的通过结果 |
| P1 | 共享空间与保留数据被低估 | F05/F06/F17：容量包含构建、暂存、保留证据、备份及 inode；引用跨崩溃保留，磁盘软管理不冒充硬限额 |
| P1 | 页面或诊断成为另一套事实及隐藏执行入口 | F10/F12：断线、无权与空结果分别显示；快照过期可见，旧会话/项目的迟到响应失效；读取不启动模型或重放写入，维护时不绕过执行闸门 |

这些门槛的实现仍属设计选择；不能以历史上出现过故障为由，引入通用工具网关、全量流量拦截、任意历史自动修复或额外人工审批链。
