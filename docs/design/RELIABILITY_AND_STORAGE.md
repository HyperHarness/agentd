# agentd 事务恢复与成果存储

日期：2026-10-28。状态：从零开发的候选设计，尚未实施。返回[架构总览](../SOFTWARE_ARCHITECTURE_PROPOSAL.md)。产品范围与 R/D/H/P/F 标签以[需求基线](../PRODUCT_REQUIREMENTS_BASELINE.md)为准；本文拥有本主题的行为规则，字段与路由由[可执行契约](../../specs/agentd_v1/README.md)维护。

## 1 状态组合与不变量

**[D 待评审]** `current_execution` 指当前执行代次，`current_candidate` 指当前待判候选；历史执行和候选另行保存。未闭合 Execution 包括启动已预留、进程状态未知及停止未证明的情况，不只是在运行的 PID。调用不能自行改写这些字段。

| Task 组合 | Execution 约束 | 候选与租约约束 | 允许情况与禁止事项 |
| --- | --- | --- | --- |
| queued，无取消意图 | 不存在未闭合 Execution；上轮已证明停止 | 无当前待判候选及有效租约，旧拒绝候选保留为历史 | 可等待依赖/容量。启动预留在同一事务把任务改 running，不能 queued 下悄悄启动 |
| running，无取消意图 | 恰有当前执行代次；最多一个未闭合代次 | 无可领取的 current_candidate；可以有私有暂存文件 | **允许没有活动进程**：启动准备中、已确认中断或重启待核对。零 PID 不等于可重试；副作用和停止未核清仍占位 |
| reviewing，无取消意图 | 所有 worker 执行已闭合，允许零活动 Execution | **恰有一个**不可变 current_candidate，其完整性/交接已核验；最多一个有效审核租约 | reviewer 离线、租约过期可无有效租约。租约有效或过期均不得替换该候选；只能重领原候选 |
| 任一非终态，有取消意图 | 停止未证明则保持原执行与资源占位 | 原候选可保留，租约必须在登记取消的事务内失效 | 禁止派发、resume、新候选生效、新领取/续租和判决生效；只允许读取、停止、核对和取消完成 |
| finished | 创建终态时所有受管 worker 执行已闭合，不得有待停止 worker | 保留最终候选/判决引用，无可领取候选及有效租约 | outcome 只能 passed/review_failed；不可修改业务合同、重跑或重新计分。外部 reviewer 客户端活着不等于有 worker 残留 |
| canceled | 所有所属 worker 执行已闭合，无预留或停止待核对 | 无有效审核租约；候选及部分成果保留 | 不可恢复成运行状态，后续需求另建任务 |

全局不变量：同一 Task 至多一个未闭合 worker Execution，同一 worker 槽至多一个占用；拒绝次数在 0–3 内且只随唯一有效 REJECT 增长。passed 可在拒绝数 0、1、2 后产生，review_failed 必须为 3。三次限制是候选审核次数，不是进程启动次数。

若在 finished/canceled 后发现遗漏进程、成果损坏或实现违反闭合约束，这是**完整性事件**，不能当作合法的“终态仍在停止”组合。保留终态和原证据，隔离受影响执行槽、停止新派发并修复；事件及成果可用性对主线可见，不偷偷重开任务或继续累加审核。只有重新确认停止才能解禁槽位。

## 2 状态转换与副作用边界

**[D 待评审]** 以下每项事务都复核当前角色、取消意图、版本和幂等键。表内外部动作不与 SQLite 原子提交；具体故障判定见[五条关键路径的故障窗口](#8-五条关键路径的故障窗口)。

| 前置条件 | 触发事件 | 事务内变更 | 事务外动作 | 禁止动作 | 崩溃后的处理 |
| --- | --- | --- | --- | --- | --- |
| 客户端草稿，合同和依赖合法 | submit_task | 写固定 TaskSpec、queued、事件及幂等回执 | 异步准备输入 | 先启动后补任务；服务端编辑 queued 合同 | 原 key 查回，未提交则同 key 重做 |
| queued，输入已解析，槽可用 | 首次派发或返修派发 | 固定 ResolvedInputs/Assignment（仅首次）；预留槽、写 launch_id 和 Execution 意图；改 running | 启动受门控监督器 | 未持久预留就启动；再次择模覆盖旧 Assignment | 按 launch_id 查启动证据，未知保留槽 |
| running，执行闭合、候选校验通过 | 候选发布提交 | 绑定唯一 current_candidate、改 reviewing，写队列事件/outbox | 发布后的读取和提醒 | 残留进程仍可改候选时待审；覆盖已有候选 | DB 引用决定是否生效，孤立文件按发布记录核对 |
| reviewing，有效角色/租约/候选，无取消 | PASS / REJECT | 原子写判决与回执、计数、下一状态、候选归档/引用、事件/outbox | 提醒主线或排队返修 | 先计数后写判决；一次回调计分两次 | 同 key 返回已提交结果；无提交不假装判决生效 |
| reviewing，候选仍同一份 | 租约到期/defer/重新领取 | 旧租约失效，按策略生成新租约代次或等待原因 | 新 reviewer 读取原候选 | 把无法审核计 REJECT；换候选沿用旧 handle | 按候选和租约代次重新核对 |
| running，中断且未取消 | 自动或显式继续 | 核准恢复记录、有限额度、旧闭合引用；创建唯一新 Execution 意图 | 恢复会话或新会话接手 | 不明副作用重放；启动前清零轮次；旧执行仍活动时启动 | 查原恢复 operation，不用新 key 再开一个 |
| reviewing，无有效租约、候选可用、未取消 | 显式恢复审核 | 记录本次 review_reopen 授权，重新开放原候选一次领取；阶段不变 | 后续正常领取/通知 | 重跑 worker；换候选；清审核故障或拒绝历史 | 查原 operation，不重复增加领取授权 |
| 任一非终态、未取消、存在可核查等待原因 | recheck 动作 | 保存核查 operation 和既有身份；核查完成后更新观察/动作 | 有界停止/输入/内容检查 | 仅点击核查就直接启动模型或绕过未知副作用 | 原 operation 接续，未知继续等待 |
| 非终态 | cancel_task | 写持久取消意图及回执，撤销审核租约，禁止新派发 | 针对已核验身份停止所有所属执行 | 停止命令返回就改 canceled；再接收 PASS | 重启仍执行原取消，等待停止证据 |
| 有取消意图，所有执行闭合 | 完成取消 | 改 canceled，释放计算预留，记录事件 | 留存成果，发送状态通知 | 进程未知时释放占位 | DB 提交未成则用同一闭合证据重核 |

## 3 跨模块调用与事务所有者

**[D 待评审]** 下列是新实现的最小内部端口，不是公开 HTTP，也不要求沿用旧类。应用用例持有一个 `UnitOfWork`；参与模块使用该事务提供的受限仓储，不自行嵌套提交，不调用另一个 HTTP 端点完成本机原子操作。平台端口只接收精确执行/发布身份，不取得任意业务表写权限。

| 用例及事务所有者 | 同一短事务中的参与者与事实 | 事务外端口及回执 |
| --- | --- | --- |
| `TaskApplication.submit` | 接入核权；任务服务写 TaskSpec、输入保留义务、queued、幂等结果与事件 | 输入模块按固定选择器准备，不提前运行 worker |
| `DispatchApplication.reserve` | 任务服务核阶段；调度模块一次取得槽、预算和全部已声明共享资源；首次固定 Assignment/ResolvedInputs，写 Execution 与 launch 意图 | `ExecutionSupervisor.prepare/permit/observe/stop`；回执绑定 launch/generation，未知保留预留 |
| `CandidateApplication.publish` | 任务服务核本执行可交付；成果模块登记已发布内容与 pins；审核模块设唯一候选；同时改 reviewing、写 outbox 和回执 | `ArtifactStore.stage/verify/publish` 在事务前完成，提交前重核权限及取消；孤立内容按 publish_id 对账 |
| `ReviewApplication.decide` | 审核模块核候选/租约；任务服务唯一更新次数与阶段；成果引用、事件、outbox、幂等结果一并提交 | 必要内容核验在长事务外完成；提交时核验内容代次/保留状态未变；不得在持有数据库写锁时遍历大文件 |
| `RecoveryApplication.resume` | 消费当前 action_ref 和处置证据；核闭合及冻结配置；记录有界恢复授权；执行恢复才创建新 launch，审核恢复只解除审核等待 | 精确副作用查询和停止核对先完成；证据过期/身份变化使提交失败，不能只凭用户点击继续 |
| `CancellationApplication.cancel` | 写取消意图、撤销租约/动作授权、保存回执；禁止后续新预留 | 对原 launch 停止；确认闭合后另一短事务完成 canceled、释放实际持有资源 |
| `RetentionApplication.collect` | 成果模块在无有效 pin/未决发布下把对象标记 retiring；与新 pin 申请互斥 | 删除精确对象后记 tombstone；删除不确定时核对同一 GC operation |

任务阶段与拒绝计数只能由任务服务修改，配置版本由配置模块创建，资源预留由调度模块管理，租约由审核模块管理；“共享一个事务”不等于模块可以任意改别人的表。初次 Assignment 归任务服务保存，选择算法由调度模块提供；避免两者各保存一份可变分配结果。读模型是可重建投影，不负责补写业务状态。

数据库约束至少保护：唯一 `(project_id, principal_id, request_key)` 请求记录；同 Task/worker 槽最多一个未闭合 Execution；同 Candidate 最多一个生效 Review；同 reviewer 同时最多一个有效领取；拒绝数 0–3；有效保留 pin 与 retiring 标记不能同时生效。有效性依赖时间或授权代次时须在事务中检查，不能仅靠静态唯一索引表达全部业务规则。

SQLite 的原子性覆盖数据库事务，不能顺带包含 Git、进程和远端写入；这正是发布/启动 journal 与对账的用途。[SQLite 原子提交说明](https://www.sqlite.org/atomiccommit.html)描述了存储与锁假设，具体 WAL/同步设置仍须按[验收顺序与复杂度控制](VALIDATION_PLAN.md#1-验收顺序与复杂度控制)目标平台验证。这里不采用完整事件溯源，也不把所有模块变成消息服务。

## 4 共同状态与事务

建议使用 SQLite 保存事务事实，Git 和文件系统保存大产物。单 daemon 是业务写入者，CLI/MCP bridge 和 Dashboard 不直接写库。长时间进程调用、网络请求和实际审核不占用数据库写事务。候选文件安全发布后才提交引用；重启时区分孤立文件和已生效成果，不凭文件存在猜测成功。

跨模块用例由应用服务协调必要事务；模块只能通过其所有者接口修改业务事实，不共享任意写表权限。事务外准备完成、提交派发之前，须重核完整决策读集：任务及输入、项目暂停/维护、取消意图、当前授权、worker 可用性和容量；不能仅比较 Task 版本。准备期间撤权或暂停必须阻止启动。不引入微服务、消息中间件或通用插件框架来替代清晰职责。

## 5 审核与终态

对外使用 next_review / submit_review / defer_review；候选准备、领取和精确绑定由审核模块内部完成。reviewer 获得任务合同、完整候选和证据索引；需要时可以读取完整相关证据。主线、worker 和 reviewer 使用分离的业务身份，身份校验不意味着操作系统对可信管理员的强隔离。

提交事务完成以下动作：校验当前租约与候选 → 写入唯一有效判决 → 更新拒绝次数或终态 → 写入事件与通知 outbox。重复 submit 返回既有结果，过期或冲突提交拒绝。PASS 直接产生 finished/passed；第三次 REJECT 直接产生 finished/review_failed。没有等待主线采纳的中间状态。

**[D 待评审]** 审核接口格式错误、引用错误或材料读取失败不是 REJECT：不写有效 Review、不增加次数，返回有限字段原因；保留原候选，允许修正提交。检查环境无法作出判断时 defer，真实不满足任务合同才由独立 reviewer 拒绝。worker 使用小型显式交付合同绑定 Task/Execution、成果引用和必要证据；服务核对实际 commit/文件，不从自由文本或退出码补造成功字段。用“退出 0 但无成果”“报告类无 commit 的合法交付”“缺失审核字段”“检查环境缺依赖”分别验收。

单个候选材料损坏不得阻塞其他健康候选的领取；保留其位置、等待原因和通知，不丢弃或伪造拒绝。审核积压背压须计入在途 worker 将交付的容量，达到水位只限制新增派发，仍能接收已执行任务的成果。具体水位待定，不增加另一套任务状态机。

统计从这些已提交事实中计算，不在多个回调各自加一。后续报告缺陷或主线新建任务只增加关联记录，不重写原 Review 或 Task。

## 6 幂等与操作结果

写操作使用 request_key，在项目和稳定 principal_id 范围内幂等；认证/撤销检查优先于历史结果重放。同 key 同内容返回原结果，同 key 不同内容报冲突。CLI/SDK/MCP bridge 在网络重试前保存请求及 key；主线需要重发一次工具调用时复用原 key，不能每次生成新 key 后宣称“已幂等”。请求结果未知时查询原操作，不按目标文本猜是否重复。

审核租约按[独立审核材料、验证证据与有界租约](TASK_AND_REVIEW_PROTOCOL.md#8-独立审核材料验证证据与有界租约)的候选相关活动与显式 renew 请求延长，同时受 TTL 与绝对持有期限限制。普通 GET、ping 和 bridge 存活均不续租；一次性 CLI 退出后不假设后台 keeper 存在。租约过期后可显式重领同一候选并重新核验既有证据，不能复活旧 handle 或自动替换报告绑定。审核恢复次数/总时长与 worker 自动恢复、有效 REJECT 三个计数分开，耗尽后的主线恢复见[恢复动作与处置证据](#9-恢复动作与处置证据)。

返回结果区分：

- **accepted**：意图已持久化，工作尚未完成，例如取消处理中。
- **completed**：本次操作已完成，不代表 Task 一定成功；Task 结果单独展示。
- **waiting**：已知条件不足，保留任务，返回原因与下一动作。
- **conflict / error**：当前操作未生效或无法确认，说明是否可以原 key 重试以及应先查询什么。

不要用单一 `success: true` 同时代表请求接收、进程结束和任务评审通过。错误输出保持少量稳定类别，例如 INPUT_INVALID、NOT_AUTHORIZED、STALE_ACTION、DEPENDENCY_WAIT、CAPACITY_WAIT、RECOVERY_UNCERTAIN、CLIENT_UNAVAILABLE；详情解释原因，不暴露密钥或要求调用者理解内部部署术语。

## 7 依赖与成果

上游 PASS 解锁的是“审核成功”的依赖条件，不代表代码已在主线。下游读取精确通过候选或主线在外部准备的 base；多个候选如何整合由主线决定。整合本身也可以被定义成独立任务，其终点仍是独审 PASS。

代码成果保存受保护 Git 引用和可验证的 commit，报告与证据保存到独立成果目录。临时 worktree 与成果保留是不同生命周期。清理前核对有效保留 pin、当前执行和保留策略；历史索引不等于永久内容 pin。期限内或活动依赖中的成果不能为缓解磁盘紧张而删除，细则见[历史索引、保留义务与回收](#10-历史索引保留义务与回收)。

工具代码作为普通成果提交，可通过同一任务审核闭环。主线在流程外选择共享工具版本，新任务固定该版本。基础阶段仅需目录与固定引用，不新增强制工具晋级状态机，也不把每次原生工具调用送入 agentd 专用 broker。

## 8 五条关键路径的故障窗口

**[D 待评审]** 下列设计只覆盖启动、候选发布、审核提交、取消、恢复五类固定操作。每类 operation 保存唯一 ID、任务/执行绑定、请求摘要、当前步骤及已有证据引用；步骤按同一 operation 接续，不增加通用可编程工作流。DB、文件系统和 OS 进程不构成一个事务，必须保留“不知道”，不能从超时猜结果。

每行是后续故障注入的验收点。**[H 待验证]** 门控监督器、资源组身份、原子文件发布/fsync 和恢复核对在目标主机的行为未验证；文件系统损坏、管理员手工删除和宿主硬件故障不在自动恢复保证内。

### 8.1 启动

拟定的启动顺序：事务写 `launch_id + generation + input/config hashes + slot reservation` 并置 running → 创建由 launch_id 定位的受信监督器和受门控子进程 → 监督器持久保存 boot/进程启动身份、资源组身份与 child-ready 回执 → daemon 事务绑定该回执并核当前授权/取消 → 发送仅适用于该 generation 的运行许可 → 监督器记录许可并解除门控。门控前不能运行模型、用户命令或产生业务副作用；许可丢失时不能凭超时自行放行。

监督器需有可重新定位且可核验身份的控制端和本地持久日志；不得用裸 PID 或仅随机文件名当作身份。daemon 崩溃不应让未许可 child 自行启动。门控和许可自身仍存在提交窗口，下面明确其结果。

| 故障窗口 | 持久记录与可核对外部证据 | 恢复/重试条件 | 等待或人工介入条件 |
| --- | --- | --- | --- |
| 启动意图已写，尚未调用 spawn | DB 的 launch_id/预留；无监督器不等于一定未 spawn，须查询该 ID 的监督记录及边界 | 只有证据表明未启动且无子进程/许可才可用原 operation 继续；不是另起 launch_id | 查询失败或无法排除已创建进程时保留占位 |
| spawn 成功，但执行身份尚未写入 DB | child 仍受门控；监督器已持久 child-ready 身份，或仍在发布它；无运行许可不得 exec | 按 launch_id 找回监督器、核对进程/资源身份后补齐 DB 绑定，或确认门控 child 停止后结束本次准备 | 监督器身份/日志缺失而进程可能存在，先查清/停止原边界，不重启替代 worker |
| DB 已绑定，运行许可发送前后崩溃 | DB generation；监督器许可/门控记录；真实进程和资源组观察 | 明确尚未消费许可时可幂等处理原许可；已运行则接回观察，不再 spawn | 许可是否消费或副作用是否发生不明，进入核对；不能拿“没有最终结果”当未运行 |
| 已执行，完成回执未入 DB | 监督器终止/输出记录、候选暂存、进程与后代闭合观察 | 验证同 launch_id 的实际结果后补记；没有结果但确认停止时按恢复路径处理 | 活动后代、身份变化、结果和副作用不明则保持中断，不释放计算预留 |

不能把“启动系统调用没有返回 handle”判为未启动。无法保证上述门控前无业务执行的主机后端不得以同等可靠性发布；不能用进一步堆叠主机框架掩盖探针不成立。

### 8.2 候选发布与成果完整性

拟定顺序：worker 闭合证明 → 私有暂存中验证成员及内容 → 写不可变 manifest/摘要、fsync 文件及目录 → 同文件系统原子发布不可变对象 → 单事务校验当前 Task/Execution/取消并写 Candidate、Artifact 引用、reviewing 和 outbox。跨文件系统移动不当成原子 rename；先复制进同一存储暂存区再发布。Git 对象及所需引用也纳入保留清单。

| 故障窗口 | 持久记录与可核对外部证据 | 恢复/重试条件 | 等待或人工介入条件 |
| --- | --- | --- | --- |
| 暂存未完整，daemon/worker 崩溃 | publish operation、暂存成员/manifest、旧 Execution 身份 | 确认执行闭合后校验已完成成员；可在同一发布 ID 补完或保留失败暂存，不生成待审候选 | 原执行未停或成员来源不明，禁止继续发布 |
| 文件已发布，Candidate DB 事务失败 | 不可变对象及完整摘要、publish_id；DB 没有已提交引用 | 重核 Task 尚可发布、授权/取消和内容相同后同 operation 提交；若已取消则作为未生效产物保留/按策略回收 | 不把目录存在当作 reviewing；任务已转阶段或内容冲突须核对 |
| DB 引用已提交，响应丢失 | Candidate/Artifact/状态/outbox 和原 request_key 结果 | 返回原发布结果，不创建第二候选；幂等对账清理暂存 | DB 和对象摘要不一致则停止该候选审核 |
| DB 已引用，但对象后来丢失或损坏 | DB 预期摘要/manifest、实际读取失败、不可变完整性事件 | 从备份恢复**相同内容摘要**，重新核验后恢复可用性；读取和审核提交前均检查必需成果可用性 | 待审任务停在 reviewing 并撤销租约；禁止 PASS。若任务已 finished，保持原结果，显著标记成果不可用并通知主线，不静默改写或自动重跑 |

回收器只清理已确认无有效保留 pin、无活动 ReadGuard 且无未决发布/执行的对象；单纯历史索引不阻止按期回收。哈希能检测不一致，不提供内容恢复能力；备份和保留策略必须单独验收。恢复后续派发也要核验原 ResolvedInputs，不能只检查输出候选。

### 8.3 审核领取和提交

| 故障窗口 | 持久记录与可核对外部证据 | 恢复/重试条件 | 等待或人工介入条件 |
| --- | --- | --- | --- |
| next_review 已提交领取，响应丢失 | 原 request_key 对应的 candidate_id、review_handle、lease generation | 同 key 返回原领取；该身份再次领取优先找回有效持有，不再占第二项 | 原租约过期或身份已撤销，返回当前冲突/空状态，不伪造原 handle 有效 |
| 判决事务提交前断线 | DB 无生效判决；候选/租约可能仍有效 | 同 key 和原内容重试，重新核授权、租约、完整性及取消 | 租约/候选/角色已变或取消先提交则拒绝；不让旧报告跳过新绑定 |
| 判决已提交，响应前连接断开 | 单事务内 Review、计数、Task 状态、回执及 outbox | 当前获准身份用同 key 查回原结果；即使该租约因完成已关闭，也不重新执行判决或再计数 | 凭据已撤销则不向旧身份返回数据，当前授权方从任务历史核对 |
| 已提交判决，但通知未发送/重复发送 | 任务和 outbox 持久事实 | 单独推进通知；reviewer 可查自己的提交回执/事项，提醒不驱动重复判决 | 通知结果未知按适配器规则处理，不回滚判决来重发 |

提交步骤在同一写事务内复核候选、租约和取消顺序。审核中的独立 read_artifact 不修改候选；有效租约也不能授权替换候选。服务不能证明审核推理一定正确，但能证明判决绑定的是哪个冻结候选。

### 8.4 取消

| 故障窗口 | 持久记录与可核对外部证据 | 恢复/重试条件 | 等待或人工介入条件 |
| --- | --- | --- | --- |
| 取消意图提交，停止命令尚未发出 | cancel operation、Task 意图、已撤销租约、原 launch 身份 | 重启继续同一取消；对可核验的原监督器/资源组发送停止 | 不可定位原身份时不发宽泛 kill，不释放占位 |
| 停止返回错误、超时或仅父进程退出 | 已发停止尝试、监督器及资源组当前观察 | 有限次重查/针对同一身份重试；零活动后代和闭合证明齐全才完成 | 后代仍活、资源组换代、权限不足、观察未知则显示取消处理中，主线/用户处理环境 |
| 所有执行已停止，但 canceled 事务未提交 | 原不可变闭合证据和当前资源状态；cancel operation 未完成 | 重核同 generation 后提交 canceled/释放计算槽 | 证据身份不匹配或发现活动执行则保留等待 |
| 取消与判决/新派发并发 | 同一 Task 写事务版本、取消意图及操作回执 | 以事务顺序决定：终态先成则保留；取消先成则禁止判决/新预留，并停止已有 launch | 不允许 API 成功返回一个结果而后台覆盖成另一结果 |

撤销审核租约不要求停止外部 Codex 根；它只阻止该报告再生效。对未知启动窗口也必须核对[启动](#81-启动)的 launch，不能因为 DB 没有 PID 就认为可以取消完成。

### 8.5 恢复与继续

| 故障窗口 | 持久记录与可核对外部证据 | 恢复/重试条件 | 等待或人工介入条件 |
| --- | --- | --- | --- |
| 收到 resume，旧执行停止情况未知 | 原 launch/监督器身份、资源组、已保存会话和工作区；resume operation | 先核对旧边界，活动执行只接回观察；已证明停止才准新 Execution | 身份缺失/副作用不明时返回 waiting，不把重启当停止证明 |
| 旧执行已停，但某外部工具副作用不明 | 命令记录及能获取的远端幂等键、Git/文件结果、服务查询回执 | 优先查询结果；可证明未发生或工具幂等才重放，已发生则向恢复会话说明 | 不可查询也不幂等时请主线核对/明确处置，不能由模型猜测“应该没执行” |
| 恢复核准并预留，新执行尚未启动 | resume request_key、旧闭合引用、新 launch_id 与同 Task 输入/模型 | 按同 operation 接续启动窗口；并发 resume 返回已存在的尝试 | 不再创建第二个 launch，不给未明旧尝试换 key 绕过占位 |
| 新执行已启动，resume 响应丢失 | 新 launch 身份和恢复关系、操作回执 | 查回同一执行进度；不再重建会话 | 仅缺响应不意味着恢复失败，不叠加重试 |
| 原会话损坏或机器重启 | boot 身份变化、工作区/输入摘要、会话/日志可用性 | 确认旧主机执行边界已消失且副作用核清后，新会话接手原任务；无法恢复内存需如实说明 | 工作区丢失先报告；同合同重新执行需明确恢复决定，不能声称恢复了丢失进度 |
| 自动恢复额度耗尽 | 历史恢复次数与失败原因、已有成果 | 只通知/等待；显式继续经同样核查，可记录新的有界授权但不清历史 | 不结束 Task 为失败、不更换模型、不清审核次数 |

上述人工介入指提供缺失环境/副作用证据、修复条件或取消的业务处置，不是允许直接改 DB 清掉 unknown。若恢复不能在受支持环境内完成，应如实保留受阻记录并修正支持范围，不宣称“任何故障都可自动恢复”。

## 9 恢复动作与处置证据

**[D 待评审]**


`resume_task(task_id, action_ref, resolutions?, request_key)`是唯一主线恢复入口。后端在Action中给出业务标签和所需处置；不让模型提交内部phase/mode/generation。每个ref绑定Task、当前Execution/Candidate、阻塞集合摘要、资源覆盖版本、授权epoch及有效期；提交时重核整个决策读集。多个可选恢复方式返回多个带明确label的resume Action，而不是让调用者传force。

| 后端动作类型（ref内部） | 可触发条件、动作和结果 |
| --- | --- |
| `execution_continue` | running中断，旧Execution已证明停止，固定输入/工作区完好，原会话可用且无未核副作用。记录一个显式恢复授权，建立唯一新Execution；仍running，轮次/模型不变 |
| `execution_handoff` | 原会话不可用但工作区/已保存成果可用；条件同上；新会话收到固定合同、已有进度、审核反馈和已核副作用说明。不能把它报告为原内存恢复 |
| `execution_restart` | 主线选择同合同重做且原输入可恢复；界面明确提示哪些进度已丢失。旧工作区隔离保留，新工作区从固定ResolvedInputs建立，沿用原模型、拒绝次数和历史反馈；不把旧候选删除或再计一次样本 |
| `review_reopen` | reviewing、当前候选完整、无有效租约；审核恢复耗尽/暂缓问题已处置。记录一次显式审核恢复授权，将同candidate重新开放一次领取机会；不启动worker、不改candidate、不清审核故障/拒绝历史。若仍有有效租约则409，不强行夺取 |
| `recheck` | queued输入待修复、running停止证据未知、reviewing成果曾损坏等。只运行有界的停止/输入/内容核对，不调用模型或擅自授予下一次执行；返回waiting或新Action。未知执行仍保留槽位；实际内容摘要不符不能由“已修复”说明跳过 |

显式继续只授权这一次恢复/重新开放，不将自动预算补满或清零。Task冻结的自动恢复策略和累计历史不变；后续自动恢复是否仍有额度照旧计算。审核恢复与执行恢复使用独立累计计数；有效REJECT计数另存，不由这些动作修改。自动审核恢复采用Task内有界策略，候选初次领取不计故障恢复，失联/暂缓后的重复领取计入对应恢复历史；defer不能形成无间隔无限领取。

动作所需证据与调用方处置分别由 [models.ResolutionRequirement / Resolution](../../specs/agentd_v1/models.py) 定义；枚举、字段及样例由生成参考维护。

只接受当前Action要求的issue与允许decision；操作身份和时间由后端记录，不由body自报。外部回执/人工说明标明是调用者提供的事实，不伪称服务独立验证；项目允许时主线可提供自己已查询的远端证据。不可用简单operator_statement代替OS进程闭合、输入摘要或容量检查。不可查询且不幂等的外部副作用必须明确处置，不能默认safe_to_repeat；若原生会话可能自动重放已完成工具请求，原会话继续动作不可用，改为带处置说明的新会话接手或继续等待。

主线可提供任务内业务处置，管理员可修复资源/凭据/存储；reviewer只能defer、提交证据和重新领取获准队列，无权为Task补预算或重启worker。所有恢复操作拒绝 `force`、`ignore_stop`、`reset_rejections`、`model_id` 等绕过字段。条件不满足返回operation.waiting和精确原因；修复后重新读取Action并提交新请求，原operation历史不改。若同一恢复operation尚在accepted且已有launch意图，新的key也只返回已有尝试/冲突，不能再建Execution。

## 10 历史索引、保留义务与回收

**[D 待评审]** 数值均为 P 建议初值，须在对应版本验收前选择。


存在有效保留 pin 的内容不得删除。Task/Candidate/Review 的 ID、内容摘要、原始判决、时间和关联是长期历史事实；单纯历史外键不是永久存储 pin。

| pin 类别 | 何时创建 | 释放条件 |
| --- | --- | --- |
| active_task | 输入、进行中工作区、候选发布、待审及可继续状态绑定时 | Task 终态且执行/发布/读取等义务闭合；然后转为交付保留策略。不得因任务长时间未活动而 TTL 释放 |
| dependent_task | 下游接受依赖时登记成功成果的预期保留关系；上游发布时转换为精确内容 pin | 下游终态且执行闭合，或者合法取消/依赖引用不成立；queued 依赖等待也必须保护未来成果，避免上游成果在下游解析前到期 |
| delivery | Task 终态时为最终成果与判决所需证据建立 | 到达已记录 expires_at 且没有其他 pin；有效期按终态时策略版本固定，后续全局改短不追溯缩短已有承诺 |
| explicit_keep | 管理身份通过 artifact keep 接口请求保留指定成果 | 管理身份显式释放；既有活动依赖不得被该动作解除，主线可查看保留状态但不获得管理接口 |
| publish/backup operation | 进行中的发布、备份开始前 | 同 operation 证明完成/安全取消；时间过期只触发对账，不能删正在复制的内容 |

内容读取使用请求级 `ReadGuard`，只防止传输中被并发删除；不延长交付保留期、不续审核租约、不确认消息或改变任务，因此 GET 不需要 request_key。请求结束释放；进程崩溃按 daemon 代次核对已有读作业闭合，维护写屏障阻止新内容读取并排空已有 guard。GC 标记与取得 guard 使用成果模块同一临界区，不能先检查后无保护地打开文件。

成果元数据字段：`artifact_id, digest, kind, bytes, created_at, availability, retention_policy_version, retention_until, pin_summary, expired_at, deletion_operation_id`。availability=available/retiring/expired/missing/corrupt；expired 是按策略回收，missing/corrupt 是完整性事件。读取已授权的 expired 成果返回明确 ARTIFACT_EXPIRED/410，包含摘要及过期事实；不把其误报成 Task 失败，也不退回“同名内容”。

GC 的必要竞争规则：

- 在成果模块临界区和事务内确认无 pin、无 ReadGuard、无未决发布/执行且到期，将对象置 retiring 并记录 deletion_operation_id。新 pin、依赖解析和新读取也在事务内检查 available；不能与 retiring 对象并发成功。
- 在事务外移入同文件系统的回收暂存区并持久记录，再物理删除；删除失败或崩溃沿原 operation 对账，不凭“目录不存在”删除历史事实。
- Git 对象由服务持有专用 retention refs；只在相应 pin 消失后按 old OID 校验删除这些 refs。GC 不改用户分支、不删除外部仓库。worktree 删除与对象保留是两步。
- P 建议暂存宽限 24 小时，**宽限不等于新的交付可用承诺**。只有仍 available 的对象可以直接建立新 pin；retiring 如需恢复应先完成同摘要核验与明确恢复操作，不能与删除竞争。
- 低磁盘仅停止新增派发/准备，并显示最大占用与可回收量；不得缩短已承诺的保留期或解除活动 pin。deleted-open 等占用按文件系统实际观测，不把 unlink 字节直接当作已释放容量。

候选保留初值建议：

| 数据 | P 建议初值 | 依据和限制 |
| --- | --- | --- |
| 未结束任务的工作区/会话/必要输入/候选 | 无自动时间到期 | 可继续与依赖是已确认要求；必须有容量预警 |
| 终态最终候选、报告、独审证据 | 90 天 | 给主线取用和缺陷追溯时间；不是永久可取承诺 |
| 其他已拒候选与必要证据 | Task 终态后 30 天 | 活动返修期间不得清理；最终失败候选按最终成果 90 天 |
| 原生原始日志、终态可写工作区及会话 | Task 终态后 14 天 | 已登记为交付必要证据的文件不受日志短期限覆盖 |
| 结构化 Task/Review/摘要/统计事实 | 首版不自动清理 | 容量单列，后续若支持归档需保留统计重建合同 |
| 已完成备份 | 保留最近 3 份且至少 30 天 | 未完成操作绑定的备份/版本不受周期清理；空间不足告警，不自动删最后可恢复副本 |

以上是 P 建议初值；未选择策略时使用 retain（不自动到期），不能由实现隐含采用上述天数删除。D 建议 V0 实现固定的 pin/到期/回收算法和策略展示；只有用户配置了明确期限的对象才可进入自动回收。数据元信息、终态和统计事实不随内容回收删除。磁盘软管理和保留策略属于既有范围，不增加任意清库入口；若阶段决定只提供 retain，须显式接受长期空间仅能预警的限制。

## 11 备份内容与旧快照恢复

**[D 待评审]**


首版优先沿现有停机/写屏障合同做一致备份，不额外承诺在线整个文件树快照。备份 manifest 包含 backup_id、源码/协议/schema 版本、数据库快照摘要、所含 Artifact/Git refs 的摘要及大小、工作区/会话范围、配置版本、保留策略、明确排除项和 completed 标记。

SQLite 一致快照不自动覆盖外部文件。备份 operation 建立所需 pin，在写屏障/状态锁下确定 DB 与引用清单；复制并核验全部承诺内容后才完成。独立密钥存储按原文默认排除，原生日志仍可能敏感。完整自包含备份完成后可以释放 live 源内容的 backup pin；若备份采用共享内容存储，必须保留备份自身的引用账本，不能因 live 引用到期而删除备份所需对象。

恢复到新状态目录并以维护暂停态启动，先核验 DB、manifest、每个要求可用的内容以及配置兼容；保留 terminal 判决和绝对 expires_at，不把恢复当作重新计分或无限延长保留。明确保留在备份中的 expired 元数据合法；备份宣称 available 的对象缺失则恢复未完成。最小演练是从完全不同目录启动恢复副本并实际读出最终 commit、报告和审核证据，不只打开 SQLite 检查表存在。

恢复旧快照不是普通 daemon 重启。安装/恢复入口生成新的 store_epoch，更新管理会话、角色凭据和根连接授权代次，使旧会话、review_handle、恢复动作引用、分页/事件游标失效；不得因恢复较早的授权表使曾撤销凭据重新有效。新接线由受信 OS owner/管理入口完成，不接受旧 token 自行换取新代次。客户端保存的每个待确认写请求同时绑定原 store_epoch；遇到 epoch 变化须显示 STORE_RESTORED 并核对，不得把旧 request_key 改绑到新 epoch 后自动重发。原 key 的“不存在”也不证明快照之后的外部动作没有发生。

恢复先保全恢复前仍存在的数据及运维记录。快照后可能发生的远端写入、已完成审核、发送通知等不能由旧库推断未发生；有关 Task/共享资源保持恢复核对待办，确认后才允许继续或另作明确处置。最小验收增加：先备份、再提交任务/撤销凭据/产生远端副作用、恢复旧备份；确认旧凭据/游标/handle 拒绝，断线客户端不自动重发，未知远端副作用不自动重跑。不要求实现任意历史合并或通用历史修复平台。

依据：[SQLite Backup API](https://www.sqlite.org/backup.html)提供的是数据库快照；Git 与文件内容的完整性由上述 manifest/pin 合同另外保证。[Git gc](https://git-scm.com/docs/git-gc)会处理不可达对象，[update-ref](https://git-scm.com/docs/git-update-ref)提供按旧 OID 校验的引用变更；因此保留引用须由服务显式管理。这里的 pin、store_epoch 和恢复顺序是 agentd 的设计，不是这些工具自动提供的整套保证。
