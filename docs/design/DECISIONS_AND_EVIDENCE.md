# agentd 设计决策与历史证据

日期：2026-10-28。状态：从零开发的候选设计，尚未实施。返回[架构总览](../SOFTWARE_ARCHITECTURE_PROPOSAL.md)。产品范围与 R/D/H/P/F 标签以[需求基线](../PRODUCT_REQUIREMENTS_BASELINE.md)为准；本文拥有本主题的行为规则，字段与路由由[可执行契约](../../specs/agentd_v1/README.md)维护。

## 1 关键选择与历史证据

### 1.1 设计选择的独立论证

**[D 待评审]** 历史故障说明风险，不证明替代方案成立。下表给出当前问题、替代方案、接受的代价及验证方式，使未读过历史记录的人也能判断方案。用户已确认的方向用 R 标识，具体机制仍需验证。

| 当前问题 | 可选方案 | 当前选择与理由 | 接受的代价 | 验证方法 |
| --- | --- | --- | --- | --- |
| 在成熟 harness 快速演进时保持 worker 能力 | 自建工具循环；封闭 recipe；原生 CLI 加监督适配 | 原生能力为 R；选择薄适配 D，把推理、MCP 和 subagent 留给原生 harness，服务只负责任务交接 | 依赖客户端兼容性，不能任意改变其运行行为；需支持矩阵 | 实际 MCP/subagent/shell、会话接续和资源归属探针 H |
| 独审需要与作者独立，且不扩成账号/线程平台 | daemon 托管审核进程；已有外部根领取 | 外部独审为 R；持久队列加外部根 D，与现有用户使用方式一致 | 外部客户端不可用时会等待，不能强制保证随时唤醒 | 真实收件、领取、过期与离线恢复验证 H，而非只测试发送接口 |
| 本机失败不应影响其他 worker | 只靠 worktree；资源监督加独立状态；恶意租户级沙箱 | 可信本机为 R；独立状态加进程资源组 D，覆盖普通故障且保留原生能力 | 不防恶意同 UID、宿主宕机和任意外部共享写入；依赖主机支持 | 一个 worker 超限/崩溃而其他任务完成；共享资源冲突拒绝 |
| 多角色操作必须有一致终态且接口简单 | 模型编排大量 CRUD；万能 action API；有所有权的业务模块 | 深模块为 R；单服务、有限业务入口和必要原子事务 D，降低调用方需要维护的状态 | 模块内部逻辑更集中，需明确数据所有权；单机容量上限 | 从 submit/next_review/submit_review 真实走通，状态/幂等边界测试；不以文件数判断解耦 |
| 复杂完成链增加终点歧义 | 审核后采纳再整合；PASS 结束 | PASS 终态为 R；项目整合在流程外 | 已通过但未采用或后来发现缺陷的任务仍保留通过记录，需关联新任务 | PASS 不再要求额外操作；历史结果不随主线偏好改写 |
| daemon 停止后谁完成升级，且 worker 不能挤垮控制面 | daemon 自行原地升级；共享父池 P/S/C 加外部协调器；单服务分组加独立生命周期执行器 | U 统一安装/升级/卸载且位于 S 外为 R；具体控制/执行分组及启动方式为 D；按需保留资源约束，不默认创建共享 P | API 有停机窗口，须验证资源余量及独立执行器；不保证 worker 不停的热升级 | 停止旧服务后协调器仍可执行；按操作记录恢复；worker 超限不拖垮控制面 H |
| 中断、等待与失败容易混淆 | 每种异常新增 Task 状态；阶段与执行观察分层 | 五阶段加组合约束 D，保留中断可继续这一 R 要求 | 状态组合仍需校验，名字少不等于复杂性消失 | [事务恢复与成果存储](RELIABILITY_AND_STORAGE.md#1-状态组合与不变量)逐行验证合法组合、取消竞争和恢复 |
| 简单完成率对未结束任务有偏差 | 只用最终 PASS 比例；复杂能力模型；固定窗口和有限随机对照 | 按模型和难度学习为 R；固定成熟队列 D 保留未完成分母，避免过早偏好 | 需要等待窗口，受同难度内容差异和共享容量干扰；不能保证因果结论 | 成熟队列门槛、随机对照、时延/用量覆盖率；见[需求：benchmark](../PRODUCT_REQUIREMENTS_BASELINE.md#7-benchmark) |

### 1.2 这次开发暴露的问题

**[F 已有事实]** 以下概括截至 2026-10-27 的仓库审计和既有验收记录；涉及较早快照时另注明日期。读者无需查阅历史文件即可理解问题。事实说明旧方案的代价和缺口，不自动证明新方案有效。

| 问题 | 当时具体发生了什么 | 对本次设计的直接启示 |
| --- | --- | --- |
| 基础设施有进展，业务闭环仍不可用 | 到 2026-10-27，轻量方案已有服务持久化、执行拓扑、资源策略和固定探针等实现及离线检查，但完整 worker 业务执行尚未获准，真实主机、客户端和同一任务端到端验收仍未完成。硬磁盘配额所需管理员能力又被暂缓，形成“基础组件完成但普通任务不能运行”的局面 | 首个版本按真实用户旅程交付，先确认支持主机和必要条件；不能用基础模块进度代替产品可用性 |
| 托管 reviewer 增加了另一套运行系统 | 旧设计由 daemon 管理 Codex 审核进程，需要处理账号运行环境、协议、线程和子进程生命周期。实现还要区分启动失败、进程 panic、仍有心跳但审核已断开、后代未停止等情况。该运行方式后来退役，改用已有外部 reviewer 根线程 | agentd 管审核队列和判决，不接管 Codex 的账号和推理生命周期；代价是客户端离线时需等待，而非由 daemon 强行创建替代线程 |
| 文件拆分没有阻止核心耦合 | 2026-10-13 的代码快照中，Service 直接继承 25 个 Mixin；另有 37 个模块仅为取得错误类型就依赖整个 Service。说明部分模块依赖的是“大服务”，而不是有限职责接口 | 用数据所有权和有限业务接口判断模块深度，不用文件数或目录层级判断。这个快照揭示依赖结构问题，并不证明 Mixin 或某个模块数量本身必然导致故障 |
| 领域需求进入通用运行前提 | 旧开发混入了特定项目的逆向恢复资料、专用工具和设计执行能力。后来领域资料迁回业务项目，专用设计执行被撤回；历史任务和证据仍需保留，不能随功能删除 | 通用平台只理解任务、输入、候选和证据；业务期待与专用流程由项目提供。普通软件项目不能因没有某领域运行时而无法安装或执行 |
| 元数据展示压过了真正需要评审的内容 | 一次真实评审记录中，完整清单约 1.58 MB，一条工具输出约 1.05 MB；初次清单展示被截断，随后通过定向读取和本地成员哈希核对补齐。大输出涉及元数据呈现、模型读取方式和项目工具输出，不能单独归罪某一工具 | 默认提供摘要和索引，按需读取完整必要材料。缩小展示量不能减少核验范围，更不能把截断输出当成完整检查 |
| 测试账本完整不等于产品验收通过 | 2026-10-26 冻结版本 `1f8bba05` 收集 22,704 个 Python 测试节点：22,572 PASS、43 SKIP、28 环境未验证、59 夹具故障、2 产品故障；后续修复属于其他版本。测试阶段墙钟约 8 小时 57 分，包含启动、协调、修复、空间整理与等待，并非测试一直运行 | 区分产品、夹具和环境问题，分别记录精确版本和验收层次。离线通过不能替代真实模型/主机闭环；也不能仅据耗时或用例数量断言“测试太多”就是根因 |
| 服务升级同时涉及进程、资源和版本所有权 | 旧方案采用 P/S/C：P 为服务外父资源池，S 为 agentd 服务，C 为服务内控制子组；升级由独立协调器在旧 daemon 停止后继续备份、切换和启动。旧版本准备与实际切换分开，切换仍要求执行闭合和正式停机 | 不能把它误称为已经支持零停机热升级，也不能在简化时只删除 P/S/C 名称而忘掉独立升级者、资源余量和锁交接。新拓扑是待验证的职责收敛方案，不是已证明更先进的替代 |
| 指南与程序的兼容承诺发生冲突 | 审计时仍有指南写“启动时追加数据库迁移”，而程序实际只接受新建数据库或结构匹配的 `0030_native_sessions`，拒绝旧版本转换。读者依赖不同入口会得到互相矛盾的升级预期 | 需求、行为协议与结构契约分别保留唯一权威来源，明确版本支持范围和不支持时的行为；不能靠不断追加说明维持多套“当前规则” |

本轮讨论纠正的“自动恢复耗尽即任务失败”和“主线选择模型”是设计阶段错误，不写成已经发生过的产品故障。它们现已由 R 规则约束；新方案的有效性仍由后续验收决定。

### 1.3 历史复查补充：按重要性约束实现

复查范围（2026-10-27）：三组审查合计遍历仓库现存 195 份历史/运维 Markdown，另读架构报告讲稿；其中 143 份全文读取，其余 52 份按全部章节及风险段落审阅。排除本轮新设计稿，不声称逐个读取所有 Git 提交版本，也未重跑历史实验。以下是去重后会影响新方案的教训，不是逐条搬运历史问题。

以下将历史事实和本次设计建议分开。**P0** 表示会破坏真实闭环、成果完整性或故障遏制，相关能力首次交付前应验收；**P1** 表示会误导配置、诊断或长期运行，应随相关能力验收。优先级不是新增功能清单。约束为 **[D 待评审]**；历史结果只证明注明的版本和路径。

| 优先级 / 坑 | 已记录事实与边界 [F] | 本次约束与最小验收 [D] |
| --- | --- | --- |
| P0：附件完整，审核目标却不完整 | 旧 reviewer 视图曾把目标裁到 4096 字节；后续无损路径修复为完整冻结目标，超过整个包的限额则拒绝，不再静默截断 | 完整性覆盖目标、验收、候选与证据。摘要标明省略且可读取原文；超限有界分块或明确拒绝。用长中文目标且最后一句决定验收结果的任务验证 |
| P0：机械 Git 操作也会执行仓库程序、损坏证据 | 2026-10-05 的离线对抗审查复现 checkout hook 继承 daemon 环境、非 UTF-8 patch 损坏及多字节摘要超出字节上限；这是离线复现及修复记录，不是已知生产泄漏事件 | agentd 管理 worktree/采集候选时采用明确的非交互环境，控制隐式 hooks、filters 和外部 diff，不传无关管理凭据；项目所需转换显式处理，worker 原生 hooks 不一刀切禁用。Git/patch/产物保留原始字节，显示解码不改原件。用秘密 canary、非 UTF-8 内容与多字节边界核验 |
| P0：资源分组没有保证控制面响应 | 历史候选准备期间 task/list 超时 30 秒、静态页面超过 3 秒无响应，daemon 仍存活；后续将阻塞工作移出 HTTP 事件循环。缺少现场栈，不能归因某个函数是全部根因 | 解析、后台作业和队列均有界；复制、哈希、Git 和等待不阻塞请求循环或占用长写事务。实际放慢候选准备，同时验证查询和取消仍可受理；取消等待不等于后台线程已停止，作业闭合前不释放目录和槽位 |
| P0：坏版本必须先健康，才能修复自己 | 旧升级体系专门增加外部新版 CLI 接续路径，使 readiness 失败时也能准备修复版本；后来又形成较重的代码交接/维修链。这是既有机制及其复杂度事实，不是某次维修成功的证明 | V1 在支持窗口内保留受限本地维护入口：业务 API 不可用时仍能读取原 operation、锁、版本与备份证据，准备修复版本并给出接续或拒绝原因。切换仍须原执行闭合、兼容及单写所有权，保持原暂停；不要求伪造健康，不复制通用维修平台 |
| P0：组件测试绕过真实启动入口 | 2026-10-21 诊断版本 `99675d2` 在实际模块入口因类被加载为两种身份而失败；修复后生成配置又引用禁用审核配置和空身份文件，真实 CLI 拒绝启动。后续暂停态安装/升级通过，未运行真实 worker | 安装产物、生成配置、真实 CLI 解析和任务启动组成同一验收链。在开发源码目录外验证最终发布包及实际导入来源，至少一次让原开发路径不可访问，避免复制目录仍暗用原解释器；禁用可选组件不成为启动前置条件。服务健康、任务可运行、审核可用分别报告 |
| P0：名为原生，配置与工具却缺失 | Claude Code 2.1.289 的本地合成探针能运行部分 Bash/Agent，但空配置来源下项目 skills/hooks/agents/MCP 缺失，部分可见 skills 被非交互授权拒绝。另有真实 worker 因 Node/npm 仅存在于检查环境而耗尽轮数 | 固定模板来源和私有可写状态；worktree 不自动继承被忽略的本地文件。显式准备所需配置，凭据绑定授权来源；在实际 worker 环境验证配置加载、工具可见、授权可用及产物取得。检查工具链缺项，不让模型反复探测；不静默关闭保护性 hooks 或绕过授权 |
| P1：界面配置冒充生效参数 | Claude Code 2.1.289 合成请求中，同设 xhigh 因别名不同发出 xhigh 或 high；thinking=2048 发出 adaptive 且无数字预算；请求输出 131072/393216 均发出 128000。仅证明该版本请求构造，不证明线上中转站接受情况 | 保存请求值、来源及配置版本；另记可观测生效值和证据来源，未知保持未知。目录元数据不是实际请求证据。明确未设置/null/0/false；诊断不暗改配置或擅自发付费请求。不增加工具/CLI 版本排名或模型身份认证平台 |
| P1：一次启停配置使整个服务无法冷启动 | 旧 R84 基线 `661b078` 中，enable→运行→disable 使注册表版本 12→14，执行内容未变，精确版本绑定仍阻止冷启动；后续修复的本地回归不等于真实主机冷启动已验收 | 分开部署身份、调度启用状态和任务固定执行配置。worker 不可用使任务等待，不应使 Dashboard 无法启动；真实执行内容变化仍须新配置，未完成升级仍绑定原计划。验收启停/增减空闲 worker 后重启及旧任务接续 |
| P1：输出与退出信号被过度解释 | 合成真实 CLI 实验出现 success 类型同时带 is_error=true；历史记录有缓冲导致无输出。2026-10-20 一次 SIGKILL 缺少内核及同命名空间证据，不能判定 OOM；memory max 事件本身也不等于 OOM | 联合解析退出、原生终态、错误、资源观察和候选完整性。HTTP 200、父进程 0、心跳或页面静默都不是任务判决；区分授权等待、工具执行、模型请求和输出缓冲，按阶段及总预算判断超时。同一原生进程内重试不另启 Execution、不消耗审核次数；若观察到模型回退与绑定不符，应显式报出，不默认为原模型的能力样本 |
| P1：只留下统一错误码，原始原因永久丢失 | 旧故障只记录输出错误，未保存类型/大小；一份 4306 字节报告失败后未保留，多个校验分支共用 reason，无法追溯具体字段。后来的成功不能解释先前失败 | 原失败点记录 operation/Execution、配置、阶段、稳定子因、观察值与限额；首错与清理结果分开，后续超时不覆盖首错。公开诊断脱敏，原始证据私有且有界。用缺失/类型错误/超限及随后清理失败验证；查看状态不重跑模型或副作用探针 |
| P1：近似探针冒充实际运行 | 主机验收曾因解释器 realpath 丢失虚拟环境依赖，在目标故障注入前就退出；systemd CPUQuota 精度和 bwrap 文件传递方式也有版本/调用路径差异。另有脚本经 editable 环境导入旧 checkout，测错源码 | 探针使用实际解释器、参数、生成单元、文件传递和资源边界，注明验证层次；先证明目标故障发生，再判隔离成功。发布记录实际程序、配置与 UI 来源，不能把重建前或其他 checkout 的 PASS 借给当前产物 |
| P1：worktree 节省源码，却没有控制总空间 | 2026-10-19 测试留存填满约 4.9 GiB 的临时空间；后续一次运行因最低可用空间不足出现 99 个存储拒绝。worktree 仍产生构建、日志和证据，停止进程不一定释放磁盘 | 容量覆盖构建、暂存/发布双副本、失败证据、备份及 inode；按实际共享文件系统核算，不能逐目录重复承诺可用空间。保留引用跨进程崩溃，回收前对账；低水位停止新增工作，保留恢复材料。磁盘采样不是硬配额，deleted-open 等占用不能当作已释放 |

这些事实不证明“功能多”或“测试多”本身就是根因，也不要求恢复旧工具网关、托管 reviewer、强隔离资格链或通用历史修复系统。旧规则和新产品方向冲突时，以已确认产品要求为准；过去的修复手段只是候选实现。

还有三条来自旧机制与设计风险的约束，**不记作已发生事故**：

- 控制面应在完整解码前限制请求规模，对后台/数据库入队施加背压；合法写入的记录在重启后仍须能被受支持接口完整读取，不能“写得进、读不出”。具体限额另定，不照搬旧维修库存数字。
- stdout/stderr 持续排空，日志与页面投影使用有界缓冲；慢浏览器或断线不反向阻塞 worker。允许重建或省略明确标记的展示数据，不丢必要交付证据与终态；双管大量输出、慢消费者和最后一次交付须一起验收。
- 维护闸门按实际副作用判断。旧查询/verify 曾触发物理输入准备或状态更新；新元数据查询保持被动，刷新页面不启动模型、构建或资格探针。静态校验、启动 CLI 探针和真实模型测试明确分开；已有工作按升级屏障结算，新工作不得绕过 hold。
- 原生 subagent/MCP 的本地后代共用 worker 预算，不另建必须等待第二个 worker 槽的隐式队列。若以后增加单独受管重工作阶段，须先定义资源预留、锁顺序、取消及等待期限，防止所有 worker 持有资源互等；当前不因此新增阶段调度平台。

### 2.1 开发前需要定案的事项

| --- | --- | --- |
| 首发环境 [P/H] | 可信用户本机，原生能力与单 worker 故障遏制 | Linux/WSL2 支持组合、实际可用资源监督方式；失败时提示缺项，不自动扩成主机管理平台 |

### 2.2 以后怎样改而不反复推翻

1. **产品决定、实现选择和已验证事实分开。** 产品决定来自用户；架构总览、专题和契约源码给出实现选择；验收报告说明实际版本是否兑现，代码存在不自动变成产品要求。
2. **一条规则一个权威位置。** 产品基线拥有目标、终点和范围；总览拥有系统边界及模块职责；专题拥有状态与行为；契约源码拥有结构与传输映射。schema 和参考页从源码生成，示例不得另定义行为。旧独立接口文件只保留跳转。
3. **核心变化写短决策记录。** 记录问题、真实证据、替代方案、对用户/API/数据/测试的影响和验收；涉及产品边界时取得明确用户决定。普通参数和模块内部重构不因此新增审批流程。
4. **先验证关键假设，再展开实现。** 尤其是原生能力、资源监督、Codex 接收消息和长审核续租；探针失败先评估现有方案，不自动派生一个大型平台项目。
5. **维护工作必须有终点。** 解决原受阻操作并交回主线，不让维护根常驻成为日常入口，也不因为一次故障把所有任务都送进人工运维链。
6. **范围变更同步收尾。** 改规则时同时核对泳道、接口、统计、示例和验收；说明旧任务怎么处理。不能不断追加新规格而留下多套互斥的“当前行为”。

本轮设计用于从零开发，不宣称旧程序已经迁移，也不将研究得到的官方能力描述等同于目标主机验收。实现按[从零开发的交付顺序](VALIDATION_PLAN.md#11-从零开发的交付顺序)推进：先完成关键探针和阶段合同冻结，再交付同一真实任务链；产品阶段限制、参数取值和支持矩阵保留各自的决定状态。
