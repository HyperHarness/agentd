# agentd 交付与验收计划

日期：2026-10-28。状态：从零开发的候选设计，尚未实施。返回[架构总览](../SOFTWARE_ARCHITECTURE_PROPOSAL.md)。产品范围与 R/D/H/P/F 标签以[需求基线](../PRODUCT_REQUIREMENTS_BASELINE.md)为准；本文拥有本主题的行为规则，字段与路由由[可执行契约](../../specs/agentd_v1/README.md)维护。

## 1 验收顺序与复杂度控制

**[D 待评审]** 版本范围和允许限制只由[需求第 9.1–9.2 节](../PRODUCT_REQUIREMENTS_BASELINE.md#91-版本范围表)定义；下表是跨版本的验证顺序，不能替代 V0/V1 范围或让开发者临时删项。接口 schema、状态组合、权限与五条故障窗口都在对应阶段逐项验收。V0 的人工领取、随机路由等限制必须先被用户接受。

| 顺序 | 必须证明的用户旅程 | 不接受的替代证据 |
| --- | --- | --- |
| 1 接入与真实单任务 | 用户通过 Dashboard 配置 worker 和角色；主线一次提交；真实 worker 产出；外部 reviewer 审核；PASS 立即形成可读取成果 | 仅服务启动、页面截图、mock 成功、单个 CLI 可运行 |
| 2 三轮与终态 | 第一轮通过、第三轮通过、第三轮拒绝、重复请求、迟到判决均得到唯一正确结果 | 只测函数返回值，不走共同服务和持久数据 |
| 3 原生能力与并行 | MCP、subagent、shell 可用；三个真实 worker 重叠运行，一个中断或超限不破坏其他任务 | 三个 mock 或单模型三实例冒称多模型能力已验 |
| 4 中断接续 | 保留代码与会话，原会话恢复及新会话接手均可；自动恢复耗尽后显式继续，次数不清零 | 清空工作区重跑后声称进度恢复，父 PID 消失冒充后代全停 |
| 5 通知和离线 | 空闲根实际收到提示并领取；客户端关闭、回执不明、重复提示、重绑和审核租约过期有确定行为 | 只有发送回执就宣称唤醒/领取/审核通过 |
| 6 分配学习 | 冷启动无品牌预设，样本充分后困难任务分配偏好变化，新模型有积累样本的路径 | 预设强弱列表、单次成功、工具版本校正替代用户要求的模型统计 |
| 7 有限运维 | 选定拓扑的资源隔离、独立 U、停机后的升级接续、写入屏障/锁交接、支持窗口备份升级及保留数据卸载 | 临时 mock 安装、不同版本测试结果拼成生产兼容证明 |

每条验收记录注明源码版本、主机/客户端/模型配置、输入、实际结果与证据。离线状态与协议测试、真实客户端、真实模型、目标主机验证分别列 PASS / FAIL / NOT RUN；缺少某层就保留缺口。

开发验证优先覆盖状态转换、幂等/竞争、原生适配和同一用户旅程的边界。全量回归按候选版本执行，日常用有依据的定向集；失败区分产品、夹具和环境，记录实际时间及资源。不要为了“深模块”删除有价值的边界检查，也不要为内部字段搬迁新增大量镜像测试。

新增机制进入默认路径前回答四个问题：它解决哪条已观察到的用户问题？现有模块能否直接处理？调用者新增了多少步骤和概念？如何证明收益并撤回？没有具体问题和验收，就留在可选设计中，不扩展核心任务合同。

### 1.1 从零开发的交付顺序

**[D 待评审]** 以下工作包是实现顺序，不修改需求中的 V0/V1 范围。现有源码不作为默认骨架，旧测试只在证明新合同仍适用时转写；不为通过旧测试重新引入采纳、整合或旧部署前置条件。

| 工作包 | 形成的可评审产物 | 完成条件 |
| --- | --- | --- |
| A 支持环境与关键探针 | 候选支持矩阵、准确版本、安装运行命令、资源/原生能力/审核客户端证据 | 每项 H 有 PASS/FAIL/NOT RUN；失败项重审相关设计，不能用其他主机的结果代替 |
| B V0 合同冻结 | 唯一类型定义与派生 schema、操作清单、固定合法/错误示例、状态及恢复表 | HTTP/CLI/MCP/UI 映射一致；精确字段与限额可校验；尚未决定的 V1 项不混入 V0 默认路径 |
| C 一个真实任务 | 最小 U 安装、管理接入、worker 配置、提交、代码/报告交付、独审、成果读取 | 使用实际发布目录和真实模型，PASS 即终态；角色和证据绑定可核对 |
| D 可靠性和并行 | 三轮、取消竞争、幂等、重启接续、资源调整、三 worker 隔离 | [五条关键路径的故障窗口](RELIABILITY_AND_STORAGE.md#8-五条关键路径的故障窗口)窗口及恢复动作表逐项通过；无人工改库正常路径 |
| E V1 能力 | 依赖、通知、有限自动恢复、能力路由、U 升级/卸载 | 按需求 V1 范围验收；学习机制与实际收益分别报告 |

每个工作包记录“需求编号 → 专题协议/契约类型 → 实现入口 → 验收证据”。F01/F07/F08 对应事务与接口；F03/F04/F06 对应原生交付与独审取材；F05/F15 对应资源准入和故障探针；F10/F11 对应配置/资源覆盖及恢复；F16/F17 对应 U 与备份。追踪表随实现填入实际入口和证据，不提前把文档示例标为 PASS。前后端可在 B 后独立开发，但 C 应在功能大规模展开前联调。

B 的候选类型、生成物与样例已放入[可执行契约目录](../../specs/agentd_v1/README.md)，可独立运行离线检查；这只是合同一致性检查，不代表 D/P 定案、B 已冻结或 A/C/D 的真实验收完成。

### 1.2 支持环境、探针与量化验收

**[D/H/P]** 机制为 D，平台表现为 H，下列数值为可评审的 P 初值而非已测结果或已确认最低配置。


首发平台不应仅写 Linux/WSL2 名称。建立 SupportProfile：OS/发行版、内核/systemd、cgroup 挂载与控制器委派、文件系统/挂载类型、Git、Python/依赖、原生 CLI、资源限制、源码版本、探针证据。WSL2 是独立 profile，不能以 Linux 结果代替；Windows 浏览器接入也需独立记录。进程/资源 probe 与付费模型 probe 分开，禁止读取状态隐式触发付费调用。

| 探针 | 最小操作及必须出现的证据 | 失败含义 |
| --- | --- | --- |
| 资源委派 | 实际安装入口建立 S/C/逐执行资源组，核 CPU/memory/pids 可写且有效；读取实际祖先限制 | 无委派不能发布为受管隔离支持；Dashboard 可启动并显示 dispatch_not_ready |
| 子进程归属 | 原生 shell、MCP、subagent 及其子进程实际运行，按 launch/generation 核资源组 | 仅父 PID 属于组不算通过；已有外部服务另标 unmanaged |
| 单 worker 超限 | 三 worker 同时活动，其中一个触发可核对的 memory OOM/pids 拒绝/CPU 节流，其他两者继续交付 | SIGKILL 不是 OOM 证据；不能只测试工具 exit code |
| 控制面余量 | worker 按允许总预算持续施压，同时查询、受理取消、处理结果 | C 的 MemoryMax 不是保底；需要总量准入及实际延迟证据 |
| 停止闭合 | 有真实后代的 worker 取消，按资源组身份核 populated=0/后代闭合，验证原槽随后仅分配一次 | 父进程退出不等于闭合；未知保留占位 |
| daemon 与 S 分别退出 | kill daemon 后不重复 worker；正式 stop S 后所属进程闭合；U 继续运行 | 不同停止边界必须分别验证 |
| U 中断恢复 | 终端退出、S 停止、U 崩溃、主机重启逐项注入，原 operation_id 接续 | shell 后台启动不等于独立作业所有权 |
| 文件发布/恢复 | 大文件/原始字节、同文件系统发布、进程崩溃与发布故障窗口（不冒称真实断电）、SQLite+内容还原 | 不以单文件 rename 推导跨 DB/文件系统原子事务 |

建议用一个明确参考 profile 校准，而不是把硬件数值写成所有用户最低配置：8 个逻辑 CPU、32 GiB 内存、本机 Linux 文件系统、可用磁盘至少为 `max(20 GiB, 低水位 + 本轮输入/构建/备份估算)`。参考 S: CPU 600%、memory 16 GiB、pids 2048；C 预算 memory 2 GiB、pids 256；三个 worker 各 CPU 150%、memory 4 GiB、pids 512；U CPU 100%、memory 2 GiB、pids 256。S 内还留约 2 GiB/256 pids 的监督和辅助开销。是否禁用 worker swap 另据主机测试；建议验证 `memory.swap.max=0` profile，避免无限换页拖慢控制面。所有数字只是初始候选，外部 Codex/其他应用仍需主机余量。

准入必须同时满足并发槽数、S memory/pids 保留预算与有效祖先限制；记录 U 与 S 同时运行的峰值。C 的保护值仅在目标主机祖先配置允许时生效，不能把子组设置当作全机保证。

| 验收参数 | P 建议初值 | 测量条件/语义 |
| --- | --- | --- |
| 最小真实并行 | 3 worker，至少 2 模型 | 来自现有 V0 验收，不用模拟替代 |
| 控制面规模 | 10,000 条终态 Task、100 条未结束、5 个并发只读客户端 | 参考 profile；大日志不灌进列表 |
| 列表/状态查询延迟 | p95 ≤ 1 秒，p99 ≤ 3 秒 | loopback，已认证，标准 50 条摘要页，3 worker 施压并有候选复制，持续 10 分钟，记录至少 1,000 请求及错误率 |
| 取消意图受理 | p95 ≤ 1 秒，全部请求在 3 秒内返回持久回执或明确繁忙错误 | 这是写意图/回执时限，不是全部后代停止时限 |
| 正常停止窗口 | TERM 宽限 10 秒，再在可核对同一执行边界发 KILL；30 秒内给出 closed 或 stop_unconfirmed | 未证明停止仍占位；不把 30 秒到达伪造为闭合 |
| 请求、分页与证据块 | 统一采用[契约参数候选](../../specs/agentd_v1/generated/API_REFERENCE.md#p-参数候选)中的协议上限 | 解码前拒绝超限；大证据走有界分块；不裁剪 TaskSpec，也不在此另设一套默认值 |
| active claim 观察 | 30 秒 stale，5 分钟升级为待办 | 不自动释放 claim，不表示可重跑 |
| 磁盘准入低水位 | 可用空间小于 max(5 GiB, 文件系统容量的 10%)，或 inode 可用率 < 5% 时停止新派发/准备 | 对同一文件系统合并核算；另加本次输入/构建/暂存/备份预估量；已有结果仍能尽量落盘，不能承诺防任意写爆 |
| 容量上限变化 | 超过已验 profile 显示超范围/等待，重新验收 | 不默认支持无限 Task、证据和 worker 数 |

性能试验要保存原始样本、测试源码/配置、负载组成、错误率、测量窗口和 NOT RUN；不能去掉 503/超时样本再计算快响应。首次探针失败后可以调整候选 profile 并记录原因，不能在验收报告里悄悄放宽已定案阈值。

平台依据：[Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)定义层级控制器和组状态观察；[systemd 资源控制](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)的子树委派和内存保护仍受祖先配置约束。[WSL 的 systemd 支持](https://learn.microsoft.com/en-us/windows/wsl/systemd)不自动证明本产品需要的用户级委派及停止边界成立。上述资料用于设计探针，支持结论只来自具体 SupportProfile 的实际结果。

### 1.3 接口、交付与恢复的补充验收

**[D 待评审]** 下表对应本轮补齐的合同。结果在实际验收前都是 NOT RUN；测试代码、结构检查或官方文档都不自动把它们升级成 PASS。

| 编号 | 场景与判据 |
| --- | --- |
| C01 | 从全新状态目录配置项目、输入根、私有凭据、固定模板/策略、worker 和角色；保存不启动模型；默认接线未完成可进入 Dashboard 修复；不要求旧库或人工改表 |
| C02 | submit 已提交但响应丢失，客户端重启后 B13 找回同一 Task；B13 暂未找到且原请求在途时，同 key 重发仍只创建一个。跨路径/不同内容重用 key 为冲突 |
| C03 | 凭据轮换后稳定身份可核对获准历史；撤销旧凭据优先拒绝。reviewer 只能查询自己的操作回执，不能借 B13/B14 读取其他项目或管理员配置 |
| C04 | next 返回 empty 后同 key 仍为原结果，新查询用新 key；领取过期不复活旧 handle；判决已提交但丢响应时查回唯一判决，不再计分 |
| C05 | 中文长目标的最后一句决定验收，完整提交、冻结、领取和读取无损；非 UTF-8 证据按原始字节往返；超限明确报错，缺失与空内容不同 |
| C06 | 真实 worker 使用 read/edit/shell/MCP/subagent、精确会话接续和新会话接手；代码与无 commit 报告均可交付；退出 0 但无有效 delivery.json 不生成 Candidate |
| C07 | delivery 缺字段、路径越界、部分写入、成员缺失和超限均保存原件并给出具体原因；补交使用同 Task/模型和新 Execution，不消耗审核次数 |
| C08 | reviewer 从精确 bundle/成员清单物化独立副本，worker 工作区回收后仍可取得；测试副本修改不改候选；源树已改的测试不能称原候选复验；必需 LFS/submodule 缺失时 defer |
| C09 | reviewer 自产证据上传响应丢失可查回；分段清单缺尾/错序/错总 hash/跨候选引用/循环均不能成为完整证据；判决 pin 保护所有分段 |
| C10 | GET/ping/列表轮询不延租；自然业务活动后的独立 POST renew 可延租但不超过绝对期限，重复 activity 不累加；一次性 CLI 退出不假称后台续租，过期后重领原候选并复核才能提交 |
| C11 | reviewing 恢复耗尽后主线执行 review_reopen，只开放原候选一次领取，不启动 worker；副作用处置与同合同重新执行留痕，不能用人工“已停止”声明替代 OS 闭合证据 |
| C12 | 4 GiB 任务 OOM 后，保存该任务 8 GiB 覆盖再恢复仍是原模型/配置；单改 worker 新配置不改变旧任务；draining 支持旧任务返修、disabled 明确等待，取消不能被恢复 |
| C13 | 冲突共享资源只准一个写入者；取得 claim 前不发生共享 namespace 副作用；daemon 崩溃或观察超时不释放未知持有；外部 reviewer 资源不得冒称受同一内部锁保护 |
| C14 | 历史索引存在但无 pin 的到期内容可回收；active/dependent/delivery/keep/backup pin 和 ReadGuard 阻止冲突删除；新 pin 与 retiring 竞争只能一方成功，删除失败沿原 operation 对账 |
| C15 | 备份包含完整 DB、Git 和证据；在新目录恢复并实际取出代码/报告。恢复旧快照后旧凭据、epoch、游标/handle 拒绝，客户端不能自动重放快照后请求，未知远端副作用不重跑 |
| C16 | 项目默认模板和资源注册表在提交后变化，queued Task 仍用提交时版本；读取/物化/续租、模型执行和生命周期操作的责任分开，UI 的 accepted/waiting/错误不得显示为任务成功 |
